# Candidate execution replay and PAPER failure authority

Decision closure date: 12 August 2026.

This addendum is controlling for Candidate DB/RPC/backend and normal CloudTMS Office Candidate API implementation. It does not change financial calculation, Banking Pay, Policy X, invoice, payment or settlement authority.

## Semantic mutation replay

An idempotency key identifies one semantic request, not one set of server-generated bytes. Every factual Candidate workflow mutation, component preparation, missing-week/no-work mutation, manager mutation and finalisation entry point requires the caller's bounded key; the backend must never manufacture a random replacement when the caller omitted it. The durable workflow receipt binds workflow, action, expected generation, caller/channel and factual client inputs. Generated manager email/token values, `SELECT_PHONE_APPROVAL.expires_at_utc`, render storage paths and official-presentation material are execution details and cannot make an otherwise exact retry conflict.

`WORKER_SUBMIT` requires the factual `candidate_signed_at_utc` supplied by the Candidate client. The backend does not substitute wall-clock time. The backend builds the semantic request and probes the durable receipt before rebuilding mutable workflow, financial or presentation material. The first successful response is durable. Reusing its key for a different action or materially different factual payload returns `CANDIDATE_IDEMPOTENCY_CONFLICT`.

The signed submission identity contains factual claim/signature input only. It never includes a regenerated official-review presentation. Where a valid standalone expense submission has no target row yet, the backend derives one deterministic provisional target identity from workflow, generation, key and stable contract/week facts; it never introduces a fresh random UUID on replay.

`REMIND` and `RENEW` bind the exact approval-request ID and request generation carried by the server action envelope. The backend and SQL both load that exact request. They never replace it with whichever request happens to be newest when the call arrives.

## Public authentication replay

The database auth receipt remains the one mutation owner. `ACTIVATE_PASSWORD`, `LOGIN_SUCCESS` and `REFRESH_SESSION` reconstruct the returned private refresh token from the receipt result's session ID and retained token-key version after the RPC returns. A concurrently losing local session proposal can never control the returned token. The public broker derives a stable opaque public session UUID for each immutable private session and seals the frozen private access/refresh result into deterministic authenticated v3 envelopes. V3 embeds the issuing key version; a separate HMAC identity selects a distinct AES-GCM key for every canonical plaintext, so one fixed IV is never used for different plaintext under the same key. The database result freezes the public access, refresh and session-mapping versions. Explicit reader catalogues support approved v1/v2/v3 overlap and version retirement.

Selected-candidate access uses the original signed access issue time. PHONE handoff responses include the approval request's frozen creation time and expiry before broker sealing. Consequently exact selection and PHONE replay return the same public access or handoff token rather than merely an equivalent newly wrapped token.

Logout and password change recover the exact database receipt once more if concurrent mutable session or old-password validation fails after the initial receipt miss. A missing receipt preserves the original authentication error; a different request under the same key remains an idempotency conflict.

Push-token storage and semantic identity are separate. The broker continues to use randomized authenticated encryption for the stored raw provider token and embeds the storage-key version in the ciphertext. It also creates a versioned HMAC over environment, provider, public session and the raw token. During approved identity-key overlap it supplies one proof per configured reader version; the private receipt metadata freezes and reselects the original semantic version before recomputing the request hash. The same factual registration therefore replays despite a new storage IV or supported key rotation, while changing the token, provider or session under the same caller key conflicts. No raw password, refresh token, challenge token, PHONE token or push token is written to an ordinary audit receipt.

The public authentication route catalogue is closed. Challenge start/resend validates the bounded caller key and preserves mandatory 400/409 idempotency outcomes while masking only eligibility/account-state results. Logout is authenticated: the broker opens the public access envelope and supplies the exact internal bearer to the private logout receipt owner. PHONE selection binds the initiating public session and optional supplied device digest into the semantic workflow receipt before token generation; another session or changed supplied device under the same workflow key conflicts.

Key rotation and rollback are paired deployment operations. Database/private response support deploys before the public writer changes. The new broker writes only a version that the private durable result can freeze, the current broker can read and the approved rollback configuration can read. An operational rollback uses this same version-aware build with the former writer version restored and all credentials issued during the new deployment retained in reader catalogues until their bounded lifetime ends. A pre-v3 binary is not an approved rollback target.

## Finalisation replay

Weekly, PHONE, PAPER and DAILY finalisation first probe durable finalisation completion using workflow ID, original generation, immutable approval/PAPER identity and actor/channel. Completion is independent of whichever valid trigger key first reached finalisation. EMAIL/PHONE identity binds the exact approval request ID, request generation, method and immutable review digest; PAPER binds the exact returned manifest. An exact replay returns the committed `FINALISED` result before current generation, current state, current row signature or regenerated DAILY materialisation is considered. A caller that presents a different immutable approval identity cannot inherit another approval's result. If no receipt exists, every current-state, signature, approval and canonical materialisation check still runs before mutation.

The PAPER return sequence remains one composed journey: `PAPER_RETURN` may replay its `RECEIVED` transition receipt and the subsequent finalisation probe must still return the existing `FINALISED` receipt rather than downgrade the HTTP result to pending.

## PAPER execution state

The exact `TIMESHEET_QR` outbox row owns the PAPER preparation execution state for one workflow, delivery generation and manifest.

- `PREPARING`: normal work before the recorded preparation deadline. It is not retryable.
- `FAILED_RETRYABLE`: a closed transient error code, durable attempt count and `next_retry_at_utc` exist. Automatic execution waits until due.
- `FAILED_TERMINAL`: the scheduler and Office retry stop. The held mail stays inert and immutable evidence is retained.
- `READY`: the exact complete-pack receipt is installed and the held mail may proceed through normal provider fencing.
- `RETIRED` or `STALE`: no preparation or retry authority remains.

Every assembly attempt has a unique operation ID and acquires one database-owned ten-minute attempt lease. The scheduler and Office retry share it. Only a newly acquired claim may execute R2 reads or pack assembly; replay of a prior `CLAIMED` receipt is observational and never authorises a second executor. Only the matching operation ID and token may release the complete pack or record the attempt failure. Retryable failures use bounded backoff of 1, 5, 15 and then 30 minutes. The durable attempt count advances for every actual claimed attempt, including attempts that end in a document timeout. A later attempt may recover an expired lease; an active lease cannot be duplicated.

Canonical enqueue records `candidate_paper_pack_preparation_started_at_utc` and a 15-minute deadline. A missing or non-ready source document remains `PREPARING`, including after the deadline: pack retry cannot make an upstream document ready. Only after the exact source document is ready can an assembly-stage transient failure become `FAILED_RETRYABLE`. A document marked failed is terminal. A missing exact outbox receives a workflow-level durable operational receipt so it cannot disappear into a silent scheduler loop.

## Office retry ownership

The normal CloudTMS Office retry endpoint uses the client UUID as the outer operation identity and a separate attempt key for each actual claim. Office never bypasses `next_retry_at_utc`; a backoff response performs no assembly. A database-owned Office receipt stores the complete final `READY`, `FAILED_RETRYABLE` or `FAILED_TERMINAL` result and HTTP status. A concurrent exact call may receive transient `RETRY_IN_PROGRESS`, but that in-progress response is not frozen as the final replay result. Once the original execution finishes, every exact lost-response retry returns its complete durable final result. If an executor crashes after claiming, a later call may acquire a new attempt only after the ten-minute lease expires. Replaying an old claim receipt always returns `claim_acquired_new=false`. No retry response exposes an R2 storage key.

Office remains under the currently agreed authenticated `admin` boundary. This addendum does not introduce future supervisor roles or a three-state Office master switch. Candidate app sessions remain separate from Office authority.

## Canonical rejection replay

Office wrapping is defence in depth. The public service-role rejection RPC itself locks actor plus key and hashes environment, target timesheet, expected current identity, expected row signature and trimmed reason. Exact reuse returns the durable result. A different target, signature or reason under the same key returns `CANDIDATE_IDEMPOTENCY_CONFLICT` before timesheet mutation.

## Preserved decisions

Current/History membership, Current as default, no future rows, seven-day recently-paid Current membership, 16-week History, disjoint membership and descending `Week Ending 1 January 2025` presentation remain unchanged. The approved incomplete-claim warning and discard-before-manual behaviour, including recoverable `REFUSED`, also remain unchanged.
