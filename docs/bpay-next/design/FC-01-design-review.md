## Required implementation conditions

1. **Complete inventory and ordering.** Drive native `finance_case`, including CLOSED/WRITTEN_OFF history; the retained `0585:22–27` and `1242:5–8` OPEN/PAUSED Candidate index cannot seed the whole list. Use the original rule-created fact (`0300:25`), not `order_key` or latest update time. Six exact created/Candidate/type ASC/DESC indexes must match SQL collation, NULLS LAST, original-created DESC and Case-ID ASC ties. For created ASC the repeated creation tie is redundant; the Case-ID tie remains ASC. Do not reverse the entire composite index and silently reverse its tie. Candidate/Client point/filter paths need the smallest supporting prefix/lookup indexes actually used, not a false universal claim that six global indexes cover every selective predicate.

2. **Bound child work as well as reply bytes.** List native money/details only after the bounded key seed. Summary examines at most 100 native Case identities and returns exact filtered category deltas plus scanned/matched counts, last seek, next cursor and completion. The cursor must carry identical filters/currentness; terminal conservation and the nine independent categories are validated without pretending their sum is total Cases. Per-Case component/snooze/origin/FC16 reads also need an explicit finite path or honest gap/continuation; a 100-Case seed alone does not bound an all-child array/ledger scan.

3. **Deferred hooks remain metadata only and atomic.** Attach only the private native inputs affecting inventory/count/filter/sort and exact private Candidate name metadata. Recompute keys from final native rows at commit; avoid transient first-insert placeholders becoming durable keys. Do not attach the hook to its own key/revision writes or recurse through the existing metadata scheduler. Compare relevant OLD/NEW fields so bookkeeping-only updates need not rewrite keys. Preserve existing Candidate→Work→Case→task/metadata/global ordering (`1429:373–387`) and do not acquire foreign Candidate/Work/Case locks from the deferred hook. Establish a consistent key/global-revision write order even when the original caller already owns the singleton.
