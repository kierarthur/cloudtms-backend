# F-25 query transaction protocol supplement

9 October 2026. Read-only source design. Supplements the saved query outer-producer map and transport map. Root alone writes product; no SQL/runtime/tests/browser/fixtures/hosted work run. This file is saved in pieces so the root builder can use the finite owner/lifetime design immediately.

## Decision and current concrete seam

Use **one original mutation owner, one transaction latch, actual OLD/NEW row events, one genuine final owner seal**. Canonical manual-review, incident, comparison and family qualification mutations use the same protocol. A standalone query action gets one zero-member QUERY_INPUT_VERSION command at its genuine completion. A Source publication reuses its existing one/two deterministic POSITION_APPLY commands; there is no metadata command for those rows and no second clock in a row, receipt, push or FK callback. Preserve genuine source receipt/binding/lease/request/current recovered branch semantics. Audit/view/outreach-only writes are not input events.

The current 2244 migration already gives `bpay_next_input_transaction` a private xid8/module epoch, monotone ordinal and terminal phase OPEN→FINALISING→CLOCK_SEALED. 2245 settings staging/flush exists for CANDIDATE/UMBRELLA/POLICY only. 2247 receive_command allows INPUT_VERSION during settings FINALISING and marks ordinary command intake CLOCK_SEALED. **It does not yet define a PAY_QUERY owner lifetime.** Adding a bare AFTER query trigger with the settings flush is therefore incomplete: actual Source receipt publication can happen before binding, push, Local completion/manual resolution or pending-release callbacks. Those remaining actual mutations must be owned, closed and their lock/FK targets acquired before the first existing clock; otherwise the affected Source branch needs a precise final-tail refactor. Do not erase the terminal latch, let a callback reopen it, or allocate an INPUT_VERSION clock after a Source command.

There are two supported modes under the same protocol, chosen by the actual original owner, not the trigger:

1. **STANDALONE_QUERY:** all business/callback writes happen before finalization; then one QUERY_INPUT_VERSION command, receipt children and terminal seal. No financial job.
2. **SOURCE_PUBLICATION:** use the original Source publication member certificate. Preferred true-tail arrangement is to finish gate mutations/callbacks before its original command publication; where existing bindings need the publication identity first, a **bounded registered Source completion** is allowed only after an actual preclock lock/callback closure. Its existing command clock(s) stay; known later row changes stage under that one still-active Source producer and finish without any clock. This is not a generic mutation-after-clock exception: only the exact same root producer, exact registered relation/row/callback manifest and actual preheld targets may use it. Unregistered settings/query writes after CLOCK_SEALED still refuse.

The builder must choose/prove one of these two concrete Source arrangements per true root from the already saved map. A comment saying “all writes finished” at 1301 does not prove the actual 0556/1257/0700 outer closure. If finite preclosure cannot be established for a recovered branch, keep the genuine original branch's business semantics and refuse **new NEXT ordered publication on that unclosed path** rather than invent a history/version. Never turn a separately valid shared Source operation under another module owner into a global Banking failure.

This new command kind is a proposed successor, not current installed source. Leave existing settings INPUT_VERSION semantics (one settings event per command) intact.
