## F-10 exact routes and authentication correction

The six exemptions are POST history-page, POST frozen-detail, GET preparation-page, GET advice with one UUID instruction ID, POST preparation and POST command. The two existing bank-name controls remain exact POST exceptions. `bpay-next-legacy-fence.js:160–181` normalizes repeated/trailing slashes exactly as the current fetch router normalizes its segment path. Wrong methods and unknown financial routes remain fenced; adding F-15/F-17 routes later requires their own exact exception.

RESET has an authentication mismatch with F-10's Done clause. Current `requireUser` (`index.js:140892–140908`) returns null for an authenticated non-admin when passed `['admin']`; the existing Banking gate at 200127–200128 consequently returns 401. Simply pasting RESET's blocks after that gate cannot produce the required 403. Authenticate the six exact new routes using `requireUser(env,req)` without a role filter, return 401 for absent/invalid session, explicitly return 403 for `user.role !== 'admin'`, then pass the already checked user through `requireOfficeUser`. Place these exact-route blocks before the existing older Banking admin gate, or use an equivalent narrowly scoped route predicate; preserve old route behavior outside the new matches. Every new RPC must follow both checks. Wrong-method routes continue through the legacy fence; no prefix grants authority.

Preparation wakes only after the closed accepted response requests `x-bpay-next-preparation-wake: ENROLL`; page reads and unsealed selection changes do not wake work. Financial-command wake follows the accepted durable DB response. Queue send failure logs the bounded typed recovery code and leaves the accepted receipt intact; the minute discovery lanes recover missed wakes. Preserve `ctx.waitUntil`/await settling semantics. Do not turn a lost wake into a false command rejection.
