## DR22 expected-offer scope assessment

13 October 2026, requested follow-up. Exact binding is card03:618/621/633/638/643: changed recovery is shown before acceptance/sending; preview remains write-free and authoritative application revalidates native capacity. R2 §2:29 expressly prohibits a new total instruction-count limit. This addendum assesses scope only; it approves no unreviewed schema or transport implementation.

**A typed expected-offer comparison on the existing immutable PAYE_NET request is a permissible small consent-support change.** It is not prohibited merely because the existing closed request gains a bounded field. The expressly required recovery-change consent can need an original offer expectation, and the existing request is its narrow owner. Expected recovery/cash or group amounts may only cause a definite refusal before COMMITTING. They must never become an allocation amount, usable capacity, kernel carry, reservation, price, certificate, signature or authority for bypassing0290/DR37. The server still computes all proposed money independently and validates its own staged dependencies under the existing fence.

This support must retain the original command kind, request UUID, actor/worker/Candidate/frozen input and expected accepted-projection qualification. Newly supplied expected fields are closed, exact native money text/pence with native scope identities; repeated requests compare the exact original stored expectation. Original stored receipts/replays are qualified before fresh optional/required-field rules, and historical absent metadata stays absent. A lost reply retries the original bytes, not a freshly read offer. Native mismatch ends the original replacement through its existing precommit REFUSED lifecycle, preserves the old accepted projection/holds, and requires a new deliberate review and request; it must never late-refuse a partially committed replacement. Scalar metadata does not require a new command, table, clock, signing key, proof protocol or preview write.

**It does not, by itself, preserve full per-instruction consent.** An aggregate recovery/cash comparison, or a fixed number of worksheet deduction-category totals, can conceal distribution changes. For example, an offered ordered pair of same-kind recoveries A£30/B£20 and an independently staged pair A£20/B£30 both have total recovery£50 and identical cash and category totals. This can arise on a re-save when prior own holds preserve A£20/B£30, the preview proposes reusing additional disjoint capacity for A, and that extra capacity becomes unavailable before application. The original native kernel/capacity rules remain intact while the offered individual changes differ. A total/group equality predicate cannot claim those individual changes were consented to.

An exact vector must identify every relevant native instruction/component and its offered amount, distinguish omission from zero, and bind the same frozen order/scope. A single32KiB request carrying all such entries has a finite maximum entry count even with a minimal encoding. Rejecting any larger legitimate worker would introduce precisely the prohibited total count limit; truncating the vector or comparing only a prefix would silently weaken “any changed recovery.” Grouping by Case rather than instruction does not solve an arbitrary number of legitimate Cases, and fixed category grouping does not prove within-category equality. An unbounded array violates the stated request bound. No exact unbounded vector can be represented by these scalar/group fields without some other binding mechanism.

Consequently, **the finite expected totals are allowable partial support, not a complete per-instruction consent closure**. A proven existing native context that fixes the entire offered proposal could make them sufficient, but the earlier event/version census has not established such a context. This review does not recommend a digest/certificate, preview cache/table, new paged acceptance or final-confirm command, extra WAIT_FOR_CONSENT stage, total-count cap, or reinterpretation of per-Case consent as aggregate consent to conceal the limitation. Those would need their own explicit owning scope; they are not silently approved here.

**Current verdict:** scope PASS for reject-only typed expectation metadata on the original immutable request, subject to exact source review; overall recovery-change consent architecture remains OPEN for arbitrary per-instruction offers. Root should record the unclosed obligation and the precise finite-envelope limitation rather than claim that aggregate equality completes DR23/DR22.
