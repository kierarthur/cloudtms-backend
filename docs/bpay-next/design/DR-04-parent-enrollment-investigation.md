# DR-04 parent counts and failed enrolment investigation

Read-only source investigation, 11 October 2026. Product author: root agent. No database calls, tests, fixtures, product edits or runtime acceptance were performed. This note supplements `DR-04-current-investigation.md`; the original command, member order, IDs and durable jobs remain the owners.

## Immediate findings

1. `private.bpay_next_pay_run` has selected/cancelled Candidate counts, but no maintained READY, REVIEW, PENDING or preparing totals. `review_simple_run_v1` uses durable-job completion and worker `EXISTS` probes; those are not the stored counts required by future DR-06 PROGRESS. A narrow private supporting change is required if DR-04 establishes these counts now.
2. Neither the native `run_worker.status` nor `job.status` has a PENDING value. Do not add a new business status merely to match the future display label. Its precise existing blocker mapping must be settled before implementing a count.
3. `command.status` permits FAILED, but current `enroll_one_v1` has no failed-state recovery. A failed PREPARE reaches the ENROLLING guard and fails again; a failed ordinary command returns without advancing the ordered clock. Marking FAILED alone would strand command N and every later command.
4. `enroll_service_v1` currently calls the private helper without an exception handoff. An update that records failure and then re-raises from the same RPC rolls back the failure record. Durable visible failure needs a caught subtransaction and a successful typed return on the existing service seam, or an equally explicit existing handoff.
5. A blind worker-status trigger that updates the parent can introduce parent lock upgrades or worker/parent lock-order inversion. The counter design must follow actual writers' lock order before choosing the smallest private trigger or existing-owner change.

## Final narrow recommendation

Read the full DR04 card/checklist and DR06 card. DR04 RQ302 owns a durable, visible, recoverable failure of ordered enrolment; RQ310 owns once-only parent outcome counts. DR06 later owns PROGRESS, its actor/deadline display and wake UI. No separate progress reader, command kind, public trigger or counter table is justified here.

**Prefer explicit guarded calls from the existing owners to a small private counter helper, rather than a general status trigger.** There is no original parent-counter owner to reuse. A supporting private helper is justified solely to update the existing pay_run row, under its already-acquired lock, in the transaction that creates/transitions the original worker. It must never compute money, discover membership, advance a command, or perform an unbounded recount.

The smallest useful stored shape is three nonnegative bigint columns on `private.bpay_next_pay_run`: ready Candidate count, review Candidate count, and preparing Candidate count. Keep the original `selected_candidate_count` and `cancelled_candidate_count`. With a documented meaning of **pending = original selected Candidate whose worker has not begun**, future DR06 can return `pending = selected - cancelled - ready - review - preparing` using only stored values. This includes not-yet-enrolled Candidates and enrolled jobs waiting before their first successful CLAIM, including earlier-command admission. It is an arithmetic view of native membership, not a new worker status. Require the stored bucket sum plus cancelled not to exceed selected. A fourth independently maintained pending column is redundant; add it only if a literal saved four-counter contract is chosen, with the same once-only deltas.

**Semantic boundary:** the cards also use REVIEW/PENDING for an accepted input issue. Current financial owners materialise every such issue as native REVIEW, including `SELECTED_WORK_POSITION_PENDING`; preserve that result and reason. Do not silently relabel REVIEW as PENDING. Unstarted pending is nonterminal and cannot satisfy review/confirm. Technical command/job failure remains a separately recorded recoverable failure, not a legitimate-data terminal PENDING. DR06 must label/explain the chosen pending meaning; DR05's later terminal cleanup/reprepare contract must establish any additional native terminal PENDING representation itself. Adapter-only proposed states are not authority to create one now.

### Exact counter transitions and idempotency

1. **Worker creation:** CLAIM0151:139–159 already locks the original worker and inserts PREPARING only when absent. Increment preparing only after that actual INSERT succeeds; an existing worker/fresh lease/repeated queue wake has no creation delta. This moves exactly one original selected Candidate from the residual pending bucket. The counter increment and worker creation commit together. Do not increment for each claim or each page.
2. **Financial outcome:** each original PREPARING→READY/REVIEW mutation has a locked old worker and native phase/lease guards. Invoke the small helper only for an actual state change, decrement preparing and increment the corresponding terminal bucket. Preserve original summary/week-fact ordering and immutable early replay. Projection continuation may leave the job unfinished while the financial worker is READY/REVIEW: count that native status immediately, and retain the original unfinished-job gate for parent review. A helper called only at final projection jobDONE would temporarily contradict the actual worker statuses. Alternatively, explicitly define those as job-completion counts, but do not claim they are worker-status counts.
3. **Once only:** guard the original status UPDATE by its expected old status and verify its affected row before applying the delta, or retain the already-locked old/new status test at the exact owner seam. Do not call the helper again from the final Workbench phase after already counting the financial transition. An unchanged status, old successful replay, stale token or failed page applies no delta. No new dedupe table, receipt ID or arbitrary job reset is needed.
4. **Cancellation/expiry:** literal active bucket conservation also requires the existing final release owners to debit that Candidate's original counted bucket when they add the existing cancelled count. The exact current seams are simple cancel0260:453–460, Case cancel0460:361–363, and preparation expiry0510:477–498. Expiry explicitly permits no worker; that Candidate was residual pending, so only the existing cancelled increment is needed. Never increment cancelled again or fabricate a worker. For workers temporarily CANCELLING, retain/resolve the preceding counted preparation outcome deliberately; do not infer it from a now-cleared REVIEW issue or decrement twice. If implementing only pre-confirmation snapshots, state that limitation and leave a named dependency for these already-supported transitions rather than adding a global trigger by accident.
5. **Existing data:** a schema installation must initialise existing headers consistently once from their exact original worker/command bindings, including cancellation/expiry; new defaults alone do not backfill old prepared runs. That is a migration concern, not permission to scan/rebuild at each page or PROGRESS read. No database backfill was executed here.

Current terminal owners are the eight named narrow successor parents already identified in `DR-04-projection-investigation.md`: PIN0151, capture1236 including all its early terminal branches, hold1438, no-Case complete0102, Case prepare0205, CLAIM0151, public financial service0280 and the new original-job projection phase owner. Only the owners with actual creation/status changes apply counter deltas; the service/projection must not apply a duplicate financial count. Existing review2359 keeps its sealed-count, unfinished-job and nonREADY-worker gates and once-only review revision. Additional stored counter conservation is a guard, not a replacement for those native proofs or for owner E2 release before confirm.

### Required lock discipline

PIN0151:236, CLAIM0151:112 and no-Case complete0102:756 take parent SHARE before Candidate control/job/worker locks. Case0205:52 already takes parent UPDATE. For any owner that will update parent counters, acquire parent UPDATE at the **existing initial header acquisition**, before Candidate/control/job/worker locks. Apply the same correction to capture1236 and hold1438 where needed. Do not upgrade SHARE to UPDATE after locking a Candidate or worker: two Candidates holding parent SHARE can deadlock when both update the header, and parent review/cancel already locks header first. This is short transaction serialization at an existing run row, not a new global lock/framework.

Do not indiscriminately change enrolment0316's run read to UPDATE: its command→run order differs. The RECEIVED/expired zero-job branches explicitly avoid any header row lock because seal/expiry uses run→command (0316:71–116). Counter creation belongs to CLAIM, not enrolment. A private trigger would require the same early lock proof for every writer and cancellation path and is therefore larger than the explicit exact-owner delta calls.

## Failed enrolment: minimal native row and handoff

Core command1324:794–808 has **no existing failure-code/time fields**; job.last_error_code/attempt_count describe an individual financial job and cannot represent an enrolment failure before that job exists. Use the original command row. The smallest durable facts are a bounded enrolment error code and last-failed server timestamp; a native attempt count and server retry-after timestamp are justified only to enforce/describe the retry cadence. Store a closed known code or `SQLSTATE:xxxxx`, not arbitrary SQL message/detail/context, credentials, query text, payloads or opaque exception JSON.

Prefer retaining the command's original RECEIVED/ENROLLING/SEALED/COMPLETE state and recording a separate failed-enrolment marker. That avoids adding a resume-state field or breaking existing status guards, while the explicit receipt describes it as a recoverable enrolment failure. If native `status=FAILED` is chosen instead, retain its exact pre-failure status and restore only that status inside the next protected attempt; otherwise PREPARE and snooze/zero-job branches cannot resume honestly. Do not assume FAILED can always restore to ENROLLING.

Extend only the existing enroll_service0560 handoff:

1. Keep service-role/NEXT admission outside the catch. Hold the original singleton enrollment_clock lock and identify exactly `agency_sequence=last+1`; no next-command skip, new identity, alternate queue or financial worker execution.
2. Run exactly one call of original enroll_one in a nested exception block/subtransaction. On failure, all partial new member/job/count/clock effects of that call roll back. Persist the bounded failure facts on that same original command **after** the inner rollback and return a closed typed failure receipt from the existing service; re-raising would discard it. Guard that the clock and original sequence/epoch have not moved. Do not store an unrelated service/authentication failure as a business command failure.
3. On the next allowed retry, repeat the same command and sealed membership at its unchanged enrolled count. Retain prior member_no, command/member/job IDs and cursor. The native helper selects only enrolled+1 and the existing job uniqueness binds that Candidate. Clear the active failure marker only after a successful original step/progression or positively validated original waiting/retired receipt; retain historical last-error time if that is the chosen audit meaning. Successful no-progress waiting for a legitimately OPEN seal is not an enrolment exception.
4. Preserve **all** zero-job paths: single snooze, MANY parent, expired never-enrolled CREATE, PREPARATION_EXPIRY and every ordinary command branch. A later expiry/seal may legitimately change the same original command; failed-state restoration must not overwrite that authoritative transition. Capturing a stale pre-failure status and blindly restoring it after another owner changes the row is invalid.
5. Return existing progressed/last_enrolled_sequence/job_id/job_kind/job_status plus a small closed enrolment-failure fact (original command ID/sequence, code/time/retry information). On failure progressed is false, clock is unchanged and there is no newly returned job. Preserve genuine zero-job progressed:true receipts. Update the existing runtime enrollmentResult exact validator and background ENROLL handling together, so a recorded failure does not become an invalid-shape transport error or a silent successful ACK. Queue continues to carry identity only.
6. Each call/wake attempts one member at most. Reuse current queue bounded retry (background30-second delay and configured finite queue attempts) and minute recovery; an SQL retry-after can prevent a tight burst. A finite queue burst ending/DLQ is not durable command completion. Do **not** impose an irreversible automatic-attempt cap that strands N: the minute lane or a later exact original wake must still recover after the cause clears. If an explicit retry budget is exhausted, its native failure receipt must remain visible and retryable through the same original ENROLL seam; adding a new business command/retry membership is unjustified. No arbitrary new retry limit was approved by this investigation.

Failure visibility uses existing surfaces only. The service receipt exposes the recorded failure to the existing Worker lane now. The existing COMMAND history receipt can add those bounded facts if a current human-visible record is required; update that closed row contract, not a new reader. Future DR06 PROGRESS can read the original run command and the single next blocked command by native unique sequence, returning the stored recoverable blocker alongside counts. Its UI is not implemented by DR04. The proposed ACCEPTED_CANDIDATES/ACCEPTED_WORK states in `broker/src/bpay-next-preparation.js:66,173–174,329–338` are **adapter schemas only**: final SQL public preparation_page0113:54–73 does not implement those kinds. They are not an installed counter or failure reader and cannot be cited as present functionality.

## Final disposition and limits

Necessary supporting pieces: three small private pay_run counters (or explicitly documented smaller terminal-only shape), one tiny private same-parent delta helper if shared by named owners, exact worker-creation/outcome/cancellation deltas, and bounded failed-enrolment facts on the existing command with a caught same-service handoff. No new table, public trigger, reader, command kind, money engine or Candidate-wide discovery is required. The unknown/unstarted pending definition and active-cancellation bucket handling must be recorded precisely in the builder's scope; they cannot be hidden behind a generic PENDING label.

Critical issues to reject: FAILED without recovery; failure-update then RAISE; changing/advancing N+1 before N completes enrolment; duplicate counter movement at financial outcome and projectionDONE; parent SHARE upgrades after Candidate locks; blanket enroller header locks; retry cap with no recovery; broker-only kinds claimed as SQL readers; zero-default counters claimed as backfilled. All producer/Worker/minute/application acceptance remains AUTHORED/NOT_RUN in this source-only investigation. No business data or joined runtime was exercised.
