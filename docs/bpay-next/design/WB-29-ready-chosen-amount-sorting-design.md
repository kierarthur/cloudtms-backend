# WB-29 whole-list chosen Amount ordering

12 October 2026. Read-only design supplement to `WB-29-ready-chosen-amount-design.md`. Root alone changes product. **Design findings only; implementation, compilation and business acceptance NOT_RUN.** This resolves the earlier Amount-sort choice: the visible resolved Work amount must be the server's chosen-rate ex-VAT amount, and the existing Amount control must sort that same amount across the whole Candidate scope.

## Concrete choice

Use the existing `private.bpay_next_workbench_group_display.group_amount` **for READY Work presentation only** as the chosen display/sort key. Keep all Candidate/header Source summaries, item A/R/H/Source amounts, `group_contribution`, `apply_delta`, Case/accepted/reserved/issue amounts and ALL/Waiting/Action display amounts in their current meanings. No new summary money/count column is needed. The existing group-display amount index and existing keyset tuple already provide full-scope amount ordering with native kind/UUID ties. A bounded page-after-limit quote cannot provide this ordering; it is not the selected implementation.

WB12:519/536 explicitly keeps Candidate-list/header money SOURCE ex VAT before pay-date valuation. WB15:623/626/636/647 separately requires each Work group amount to reconcile to its complete expanded members. Owner F and WB29:1131 require resolved Ready Work amounts at the saved chosen rate. Owner A3e requires server ordering over the complete list. These are distinct bases, not a requirement to reprice Source summary rows. The UI must keep the Source summary qualified and use the chosen Ready group/child value consistently.

## Why the existing page cannot safely quote-before-order

Current0113 `bpay_next_workbench_kind_page_v1` permits page limit1–100 at276, and Candidate groups seed requested identities plus lookahead at899. That is a **returned-page bound**, not a bound on all Work groups for the Candidate. The existing group schema1252:32–65, display schema1946:4–29 and Candidate summary counts impose no complete-Candidate group maximum. Quoting only the first101 or10 before sorting would omit legitimate rows; quoting every current group on each page would lack a finite complete-scope bound and discard the current indexed seek. No new arbitrary Candidate cap or full current-Work scan is proposed.

## Smallest useful cache metadata and indexes

The amount column/index already exist (migration `10102026_1946_banking_pay_next_candidate_group_display.sql`:13/27). Add **two metadata fields to the existing Work group**, not a money table:

* `chosen_display_date_sensitive boolean NOT NULL DEFAULT true`: default true deliberately fences retained groups until the new display owner inspects them once; never initialize old chosen money as certified current. The owner sets false only after complete native qualification proves no mapped saved treatment or applicable native EX08 need can make this Work's current Ready/Action display date-sensitive.
* `chosen_display_pay_date date NULL`: the exact native official date used by the display owner. Sensitive+NULL is uninitialized/unavailable. Sensitive+date is certified only for that date. Insensitive groups may leave it NULL. Case groups are excluded from this support.

The sensitivity check must use bounded mapped saved physical candidates **before** compatibility filtering, as BD158 already requires, plus the exact latest native EX08 need membership. A currently incompatible saved date is still sensitive; otherwise yesterday's saved value could be certified as a timeless default. No raw historical decision/Work scan, no new need event and no guessed classification.

Add one partial due index on the existing group:

`(chosen_display_pay_date NULLS FIRST, work_id) WHERE group_kind='WORK' AND chosen_display_date_sensitive AND (ready_count>0 OR action_count>0)`.

Include the exact current complete/non-dirty qualification in the due/read predicate; if an extra currentness predicate is part of the chosen index, both callers must use the same predicate. Existing1946 amount index stays exactly useful:

`(candidate_id,section,(group_amount IS NULL),coalesce(group_amount,0),presentation_kind COLLATE "C",presentation_id)`.

This is an indexed display key plus a bounded date-repair selector, not a sorting framework, projection counter or public producer trigger. No public request, response money field, command or job kind is added by the cache metadata.

## Finite date repair through the existing lane

Use a successor of **the existing** `public.bpay_next_workbench_week_rollover_page_v1(jsonb)` parent `11102026_0255_banking_pay_next_due_recovery_pages_v1.sql`:122–215. Retain its FUTURE_WEEK body/cursor and append a second finite selector for stale date-sensitive native Work groups. This is the current WEEK_ROLLOVER lane, not a new job/route/timer or sorting protocol. Obtain the real official date through the installed date-context owner (the original FUTURE_WEEK lane still uses inclusive London date for week eligibility).

Use the same input limit as a **shared total** visit budget. Split it deterministically between the two native selectors (for example50/50 for limit100, with a finite alternating/single-selector rule for limit1); do not allow both selectors independently to visit the full limit. Retain original response `rows_visited/rows_changed/rows_deferred/complete`, Worker byte/deadline rules and existing maximum two pages per lane/tick (`broker/src/bpay-next-background.js`:170–177). `complete` is true only when both selectors are exhausted for the current pass.

To preserve progress past busy rows without altering the FUTURE_WEEK identity or encoding heterogeneous IDs, add exactly **two nullable internal seek fields to the existing Workbench revision control**: `chosen_rollover_seek_date date`, `chosen_rollover_seek_work_id uuid`. These are continuation metadata, not new counters or public cursor fields. Order the stale selector by `(chosen_display_pay_date IS NOT NULL,coalesce(chosen_display_pay_date,date '0001-01-01'),work_id)`; the stored date plus non-NULL Work ID reproduces the NULL-first tuple exactly. Seek ID NULL means start. Advance by the last visited native Work, compare-and-set the original seek, wrap to NULL after exhaustion, as original0255:203–208 does. Date changes may require the normal end-wrap before a fresh pass; reads stay unavailable meanwhile. No first100 completion or busy-prefix starvation is accepted.

Discover **both** finite native prefixes before any mutation. Prehold the union of both selectors' Candidate controls in native order, then the union of exact Work rows NOWAIT, then the original FUTURE_WEEK page's required Case preholds, **before either selector calls task/metadata/global revision or refresh**. Do not execute the old Future refresh first and only then acquire new chosen-row Work locks. Revalidate each group's date-sensitive/current/date condition under those locks. Call unchanged `private.bpay_next_workbench_queue_origin_v1(work_id)` or its exact `schedule_task_v1('ORIGIN',candidate,work,NULL,false,false)`+`mark_processing` sequence. Do not call the business Work/Case refresh directly after the scheduler has taken the projection lock unless its whole original scope was preheld before that first mutation. Deferred/busy rows retain stale date and are revisited after the native cursor wraps. Existing active ORIGIN is exact idempotent reuse, not adoption of an arbitrary lease. Successful scheduling can count as the lane's changed metadata; the sort key becomes readable only after the original task actually refreshes it.

The required existing task chain is already complete:1429 scheduler:91–96 binds native Work/current/applied/FVR/WAIT and exact `ORIGIN:<work_id>`;110–115 reuses only an exact active tuple;123–146 handles generation, metadata/dirty/pending counters. The Work core/display sees the **then-current official date**; if it changes again, the new date predicate remains stale and the same lane repairs it. No task schema/phase/lease modification is necessary.

## Read gate and ordering proof

In the current public `bpay_next_workbench_page_v1(jsonb)` parent2241, before any Candidate/header/group/member read that claims coherent current projection, use a native indexed EXISTS over date-sensitive current Ready/Action Work groups whose stamp is NULL or differs from the current official date. Use separate indexable NULL / less-than-date / greater-than-date probes if needed, each `LIMIT1`; do not aggregate/count the stale inventory. Return the existing `BPAY_NEXT_WORKBENCH_PROJECTION_NOT_CURRENT` shape, with existing native counts unchanged, until repair completes. This closes the first-read window before the minute lane has scheduled a task; original dirty/pending controls then cover the in-progress repair. Do not invent a fake positive dirty count or perform writes from the STABLE reader.

When that gate and original adoption/dirty/pending gate pass, every sensitive chosen Amount index key belongs to the current official date and ordinary native W11 revisions. Current0113:565–566 then seeks/sorts **that same visible group_amount** over the whole scoped display relation, with `(presentation_kind,presentation_id)` unique ties, before899 limits output. Current2241:459–465/1057–1060 binds date plus Workbench/adoption revision to the cursor. A date or changed amount invalidates continuation; no post-limit retagging is allowed. Native child quote/date equality can fail closed if its exact operands no longer match, but must never silently show a different outer amount.

Source Candidate/header summaries remain maintained/literal, visibly qualified and page-independent. Their Source amount index/keyset stays unchanged. This design adds no chosen summary aggregate, no financial mutation, no new public table/trigger/command, no provider/headroom work, no synthetic Run, no Source seed/rebind and no parked F25 machinery. Actual physical performance must be measured only under separately authorized checks; a cost estimate is not a functional blocker or a claimed timing result.
