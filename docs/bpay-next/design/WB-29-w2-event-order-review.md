# WB-29 W2 event order and inclusive mapped decision carry

Read-only design review of current2044 schema/indexes,2100 guards/active reader,2135 publisher and WB29/WB33 rules. **Required remedies identified; this is not product SOURCE/runtime approval.** Root alone authors migrations/functions. ## Findings and narrow remedies

**EO01 — the command-event index is narrower than the independent decision identity.**2044:61–70 permits ACTIVE variants distinguished by target channel/Umbrella/policy/date.2100:189–227 deliberately filters only the current requested compatibility tuple; it does not enumerate every ACTIVE mapped variant. However2044:100–102 uniquely indexes `(command_id,event_kind,approved_line_id,rate_family,rate_code)`. Two old ACTIVE variants with the same based-on line/bucket can collide when CLEARED under one publication command. Even when old based-on lines differ, all carried/new versions based on the same current predecessor line/bucket can collide at SAVED. Legitimate different target/date variants are not duplicate intent.

Use a **new additive migration**, preserving the applied2044 file, to replace only that request index with an exact version-aware unique key:

```text
(command_id,event_kind,approved_line_id,rate_family,rate_code,
 decision_id,decision_version) WHERE command_id IS NOT NULL
```

Keep the existing event-version unique index `(decision_id,decision_version,event_kind)`, NEED index, decision version/ACTIVE/published ACTIVE indexes, INSERT-only event guards and deferred audit guards unchanged. There is still one SAVED and at most one CLEARED per immutable decision version across all commands. The closed W2 input rejects duplicate requested identities; native ACTIVE compatibility uniqueness and explicit mapped-closure duplicate checks reject conflicting choices. The revised event key allows actual independent versions, not duplicate caller intent or `ON CONFLICT DO NOTHING` omission. Do not drop event uniqueness wholesale or fabricate a separate POSITION_APPLY command per carried row merely to evade the index.

**EO02 — compatible-only carry is incomplete.**The current command design step4/7 says to carry compatible siblings and refuse incompatible siblings. A normal Candidate channel/Umbrella/date change leaves valid saved ACTIVE variants whose target/date differs from the current offer. Blanket refusal blocks the card's required new decision; carrying only the current compatible subset strands other variants on the old boundary and prevents a later exact-owner CLEAR. Enumerate **all structurally mapped ACTIVE variants** for the locked predecessor, independently of their financial compatibility with today's Candidate/date. Preserve every unrequested variant through the complete new mapping with its unchanged selected intent and native saved scope. Distinct incompatible variants are retained metadata; they are not applied or repriced for the current target.

**EO03 — carrying a manual amount must not reset its saved Position scope.**2100:88–96 currently requires every INSERT.original_position_basis to equal current Position. Simply copying a changed current A/R/H into a carried MANUAL_AMOUNT makes its old amount appear approved for a new residual. Copying the old tuple instead is currently refused by that INSERT guard. This needs one exact **server-authored carry provenance arm**, not a broad bypass of Position admission. Fresh requested SAVE retains the original exact-current Position guard. A carried version preserves the predecessor's original_position_basis; the existing quote's exact equality/full-residual admission continues to refuse applying that old manual amount when scope changed. Such a row can still be disclosed and exactly cleared.

Use the existing immutable bounded decision.request_body to retain a closed server-built carry record containing the exact prior decision ID/version, original W2 request ID and publication mapping. No public caller may supply that record. A small typed predecessor pair on this same native row is an alternative only if root prefers schema over the existing JSON audit operand; no new decision store is needed. The carry guard must positively join the exact old row, its CLEARED event for this same new publication command, the native publication predecessor/new revision, and the original/published old basis mapped to that predecessor. Check every retained selected/economic operand against that exact old version. An arbitrary JSON `carried=true` is never admission.

**EO04 — VAT compatibility and the three decision unique keys differ.**2100.active_v1 treats target_umbrella_vat_chargeable as an exact compatibility operand.2044's version, ACTIVE and published-ACTIVE unique keys omit it. Different VAT variants can exist on different original/published line identities and both map to the current boundary, then collide when an inclusive carry maps them to one new based-on line. To preserve those genuine native variants, the same additive schema support must align these three existing compatibility unique keys by adding `target_umbrella_vat_chargeable` beside target_umbrella_id (retaining NULLS NOT DISTINCT and all original predicates/other operands). This does not add a target setting or alter financial formulas; it aligns the keys with the actual retained native compatibility reader. A true duplicate with equal channel/Umbrella/VAT/policy/date still fails. Do not merge the VAT variants or rewrite either saved VAT value to avoid a collision.

## Complete current mapped closure

Under the existing Candidate→all explicit Work→Position/related Case prelocks and before seed/clock/publication, enumerate ACTIVE decisions satisfying either:

```text
(based_on_revision_id,approved_line_id) = (locked predecessor,mapped native line)
or
(published_revision_id,published_line_id) = (locked predecessor,mapped native line)
```

Require the corresponding stored basis equal the actual native basis at that boundary, same Work/Candidate/component/family/code and unchanged complete Source identity. Deduplicate the same decision ID returned by both paths; do not select max/latest to hide ambiguity. Group by mapped predecessor line/family/code plus exact target/Umbrella/VAT/policy/date. Two distinct decisions in one exact compatible group are a typed ambiguity before mutation. Different compatibility groups are legitimate siblings and must be preserved.

Bound the full physical mapped closure and encoded carry/result scope before acting. A target-filtered `active_v1` read or LIMIT after compatibility filtering cannot prove completeness. Use the2044 partial boundary/published indexes, a physical overflow sentinel and the existing resolution count/byte budgets. Refuse overflow before publication; do not silently omit a variant. Store the exact closure in memory for the transaction; no persistent snapshot/cache/protocol is introduced.

Classify every member as requested replacement, requested exact CLEAR, or unchanged carry. A fresh SAVE's expected pair refers to its current native target/policy/date compatibility group, with NULL/NULL only when that exact group was disclosed absent. It does **not** implicitly replace another group's incompatible saved decision. CLEAR names the precise persisted ID/version disclosed by W1 and native RESOLVED_AND_CLEARABLE classification; it does not clear all rows sharing a bucket, target or Work.

W1 must distinguish its current compatible selected pair from the bounded saved mapped variants and their literal target/date/compatibility/clear classification. This permits explicit incompatible-owner CLEAR after another SAVE, without pretending the old quote matches today's target. The existing row identity/pair fields can address that exact variant; no supplied financial target or units become authority. A genuine stale/ambiguous/mixed-owner classification still refuses. Finance Case clear remains delegated to the actual FC owner.

## Native publisher and event sequence

Fresh actor/NEXT/service/admin/schema checks and all existing expected Work/current/applied/physical/version/Source/economic-command guards remain. Acquire all Work locks before seed/Case refresh/clock. Recheck receipt and native offer context under that serialization point.

Current-compatible requested/used buckets are quoted through the shared helper. An incompatible carried target/date variant is not quoted as if it were today's intent and does not require today's target/window compatibility. Structural basis mismatch is a real stale/invalid mapping, not ordinary target incompatibility. Preserve Source UNBOUND proof/READY behavior.
3. Stage one complete treatment revision per Work, build deterministic old→predecessor→new line mappings for **all** mapped variants, and preserve original Source payload. Stage all finite Works before allocating publication clocks. Do not mutate decision/event rows yet to create a fake successful application.
4. Publish once per Work through2135 `publish_staged_revision_v1`. It seals/updates the Work pointer, marks Processing, receives the native POSITION_APPLY child, inserts command member/publication and returns its sequence. The child FKs now exist. Position remains on the locked predecessor while this same transaction appends decisions; do not force Position forward.
5. For each retiring old version, insert exactly one CLEARED event **while old.state is ACTIVE**, with event.revision_id/approved_line_id equal that old decision's **based-on** pair, as2100:150–156 requires. The new command ID is the actual publication child; the actor is the authenticated current action actor and the event reason distinguishes requested clear/replacement from mapping carry. Then update only old.state to CLEARED. Do not use the new published line as the old event's identity and do not UPDATE state before the event.
6. Insert each requested replacement/new selection and each unrequested carried version, with based_on_revision_id/approved_line_id at the real locked predecessor and published_revision_id/published_line_id at the one new publication. Derive both bases natively. Fresh SAVE uses its current Position tuple; carry preserves the exact prior selected target/Umbrella/VAT/policy/date/mode/manual operands/reason/original saved scope, plus exact carry provenance. Never migrate an old MANUAL_AMOUNT onto changed A/R/H or retarget an incompatible sibling to the current Candidate/date. Version allocation is deterministic under the Work lock and must respect2044's exact tuple/version uniqueness; do not use a global/version-history sweep.
7. Insert SAVED for each new version while it is ACTIVE, using the new decision's based-on pair, command and authenticated audit actor, satisfying2100:150–156. New carry audit actor/time records the actual current carry operation; the exact referenced old version retains the original choice actor/time and metadata. Do not pretend that carrier manually chose the old rate. Requested exact CLEAR has no replacement SAVED row for that owner; all other closure members carry independently.
8. Insert the original W2 immutable receipt after all mappings/events/versions succeed; retain exact child publication IDs, requested results and carried old→new pairs. Native targeted refresh/adoption is same transaction and returns truthful Processing/completion. Any failure rolls back pointer, command, events, versions and receipt together; no partial result. Preserve the existing deferred audit requirement: every new version has SAVED, every CLEARED event has final CLEARED state. Do not force constraints immediate between the event/state/new-row steps.

## Carry proof and immutable metadata details

The carry guard is an additional positively proved constructor, not relaxed user SAVE. At INSERT require the old version is CLEARED with an event naming this exact child command; that event was itself inserted under the original ACTIVE guard. The old native mapped basis must equal the new based-on predecessor basis and the complete publication must prove new.published basis/Source payload. Retain all current2100 physical/component/tax/source units/rate/charge/channel/Umbrella/policy checks. The exact original_position_basis may differ from current Position only when it equals the authenticated old immutable carry version's tuple. Every fresh intent must still equal current Position.

Choice metadata remains unchanged through carry; mapping IDs, version/command/current audit identity are necessarily new and explicitly documented. Old rows/events are not overwritten. No update to target/mode/manual values, timestamp, actor or JSON on the old row is allowed. Exact frozen Create attachments still point to old immutable IDs/versions, even after retirement; the original E2 changed-revision holdback/system-release remains. Carry does not make an old captured offer follow a new revision.

For unchanged siblings that remain financially applicable, the same preserved mode is later quoted against its valid actual residual through the same helper; no suggestion replaces a saved manual choice. For an incompatible date/target or changed saved MANUAL_AMOUNT scope, disclose its retained actual intent and compatibility=false rather than fabricating a current quote. It stays structurally addressable for exact CLEAR. These distinctions are needed to satisfy both independent decisions and saved-scope preservation.
