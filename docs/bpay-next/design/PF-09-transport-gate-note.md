## Concrete source rules

1. **Transported projection, not internal row locking.** In these final JSON-bearing owners, refuse a whole database record passed to `to_json[b]`, `row_to_json`, `json[b]_agg`, `json[b]_build_array` or a returned whole-row JSON expression. Keep their current named `jsonb_build_object` fields. Preserve legitimate private `SELECT r.* INTO ... FROM ... WHERE primary_key=...` authority checks when that row is not serialized wholesale. Current channel-Draft code, for example, locks/reads a typed `v_run`, then transports only `run_id` and `pay_channel`.
2. **Six existing derived-page serializers are explicitly projected.** `to_jsonb(page)` is legitimate in current work, worker status, channel worker, current case, case component and stored-credit readers. Each `page` is a derived SELECT with named fields and explicit decimal `::text`, not a base-table alias. Preserve the exact finite SELECT projection for each signature, including aliases and casts; reject a new `*`/`alias.*`, unknown field or a removed cast in that projection. Do not grant a broad waiver merely because the alias is named `page`. Existing fixed-query source handling can inspect the retained query text without executing it.
3. **Exact money kinds and encoding.** The current preparation wrapper separately transports `source_consumed_ex_vat`, `frozen_ex_vat`, `frozen_vat`, `frozen_inc_vat`; STATUS separately has gross ex/VAT/inc, entered PAYE NET, accepted recovery/addition and bank cash. CASE pages separately have principal counters/source components. Preserve those existing named projection clauses with every money operand cast to text. History's existing generator emits every scalar as `STRING_OR_NULL`; preserve its finite registry/templates and all 52 amount-scope labels. Do not recalculate, round or sum in the Worker/browser.
4. **NEXT schema floats.** Inspect managed NEXT relation CREATE/ADD/ALTER column declarations using existing executable SQL tokens. Reject actual `real`, `float4`, `float8`, `double precision` and `float[(precision)]` types (including `pg_catalog` qualification). The card's explicit acceptance says a float column in a NEXT migration fails. Inspect current managed NEXT migrations, not only a changed subset; inspect new NEXT column alterations in repeatables as well. Comments, prose saying “real”, private row types and nonfinancial inherited provider schemas are not float declarations.
5. **Retain existing Worker contracts.** Preserve command `INPUTS`/`OUTPUTS`, exact `Object.keys` cardinality plus required-key/type checks, `typeof value==='string'` money validation, BigInt sequence bounds and `pennies()` BigInt conversion. Preparation ROWS/STATUS_HEADER and exact validation already distinguish money/counters and nullable fields. History validates exact field lists and string-or-null scalars. Keep these checks and current limits; do not introduce a blanket `Number()` ban because byte lengths, limits and dates legitimately use Number. A money coercion or `parseFloat` is the forbidden change.
6. **Bound actual text.** Command reason is 1..1024 UTF-8 bytes; receipt/code/file each have their existing <=256 bound; CSV has <=120000. Preparation label is <=8192 and ordinary text <=responseBytes, with bounded streamed response/request envelopes. History has bounded envelopes and <=100 rows; it does not promise an individual 256-byte bound for every historical string. Keep those actual validators and byte caps, rather than invent a universal text length or removing legitimate reasons/CSV. `assertNoBrowserFinancialFacts` is an existing Source-route guard (`weekly-source/routes.js:203`), not a missing NEXT-command helper; the closed command input schema already admits only its named user inputs/evidence.

Use current F-08 reply/input allow-lists as the finite authority. D02's 13 command action schemas already retain exact decimal strings and typed identity/reply checks. No command/module product change is indicated by this read-only investigation; integration/readback and future app acceptance remain separate.
