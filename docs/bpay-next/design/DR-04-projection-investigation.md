## Recommendation

The proposed **existing PREPARE job** continuation is a sound bounded seam if every financial terminal owner enters it **before the native job DONE UPDATE**. Preserve the original worker READY/REVIEW financial result, frozen figures, reason, summary and hold facts. The job remains unfinished until both original native identity walks complete; existing review/confirm unfinished-job gates therefore remain authoritative. Do not revive committed historical DONE jobs or rerun an allocation owner to do projection. DONE followed by revival even inside one transaction is unsafe: PF06 lifecycle-clock0352:30–33 retains a false first finished_at_utc, and any once-only terminal counter could also fire early.

Each projection STEP visits at most100 original membership rows and calls the existing `private.bpay_next_workbench_refresh_many_v1(uuid[],uuid[])` in that same page transaction. Work and Case are separate phases, so combined input cannot exceed100. Cursor and projection effects commit together. No new job kind, table, identity inventory, money calculator, digest or admission protocol is justified. Existing job `phase` and `cursor_key` are sufficient; both required seeks are already indexed.
