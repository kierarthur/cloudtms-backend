## Invariant and exact association

Economic same-job staff Retry advances `worker.preparation_revision` once and preserves `captured_preparation_revision`, original accepted request target, job/command/Input identity, economic rows, active holds, Case stage and checkpoint. Proposed job `retry_execution_revision` plus the exact existing immutable workbench receipt request ID is sufficient native supporting storage if the receipt binds old/current/target execution, Run/worker/Candidate/module/job and captured revision. The current receipt's work_id is NOT NULL; its conditional nullable PREPARE branch remains required for Case-only Retry (`10102026_2150_banking_pay_next_workbench_retry_receipts.sql:14–44`).

**The execution association is sticky after successful pages.** Reset only consecutive failure count, due and attention bookkeeping after validated progress. Clearing the revision/receipt pointer would fail the next page. It is superseded or cleared only on a newly accepted native action/execution, never as an incidental successful-STEP cleanup.

For the original DR05 REPREPARE request, keep `x.target_preparation_revision` as its accepted immutable PK/lifecycle identity. Exact current-worker equality may use the validated retry execution associated with that same job/request; original target remains the request UPDATE key, actor origin, result and economic linkage. An unqualified COALESCE across every request is unsafe: a later same-job SYSTEM RELEASE accepts the then-current worker revision+1 and has its own new target. That acceptance must retire the original REPREPARE and clear/supersede the prior operational execution association; the new RELEASE target then equals the worker normally.

A finite private point helper can centralize qualification of the existing job plus existing immutable receipt. It must distinguish original job revision1, the exact original native action target, and the current operational retry revision; it cannot use the newest receipt, recursive history, caller-selected target, hashes or an invented proof protocol. The helper may be reused by the finite current predicates below. Public/native admission still applies its own status/module/deadline/order fences.

## Attention, counters and remaining design checks

Economic attention is a real REVIEW outcome: exactly once debit preparing/credit review and retain original economic stage/checkpoint. Same-job staff Retry exactly once debits review/credits preparing, changes root to PREPARING, invalidates root review revision, advances execution revision and resumes that preserved checkpoint. Do not call the entire existing begin_projection owner merely to transfer those counters: A2390–2405 intentionally saves a terminal failed checkpoint and replaces economic phase/cursors with Workbench projection. Attention does not prove capture complete.

Ordinary projection attention needs its actual prior READY/REVIEW status and existing counter bucket; explicit Retry resumes original projection without changing execution/economic revision or holds. A revision-less projection Retry must not overwrite the economic Retry receipt association with a new receipt lacking its expected/target execution fact. RELEASE PROJECT uses the separate native request/stage and is excluded from this retry ceiling, as are mandatory original release/expiry/discard cleanup. This narrowing supersedes the prior requested broad cleanup-attention proposal.

Potential fewer-change option: a single exact point helper returning the qualified current execution plus original action target centralizes the receipt validation; it does not remove twelve call-site differences where immutable request keys and lifecycle completion are distinct. The current DR05 association alone cannot eliminate them: its target is immutable, manual operational retries leave job/command unchanged, and the native worker guard explicitly permits revision changes only from the existing action. No accepted request rewrite, new ordered command, synthetic economic revision or latest-history lookup is a valid shortcut.

Design/source-only conclusions above are not runtime safety proof. Root's authored concrete receipt fields/helper predicates must be reviewed before source PASS; future joined evidence for repeat Retry, original DR05 action completion, E2 superseding release, expiry/discard retirement and real FC14 actor fidelity remains NOT_RUN.
