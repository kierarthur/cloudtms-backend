### Narrow settings receipt

Add one private append-only version receipt authority, not another mutable Candidate/Umbrella settings owner. Typed Candidate before/after fields are `(candidate_id,pay_method,umbrella_id,min_take_home_wtd)`; typed Umbrella fields are `(umbrella_id,vat_chargeable,enabled)` because delayed capture currently reads enabled as well as VAT. Retain genuine mutation/operation identity, module epoch, existing command ID/agency sequence, before/after digest, and actor when actually available. Do not copy personal/bank secrets or invent an actor from current state. A row UPDATE captures OLD/NEW in the database; it must ignore unrelated updates and equal financial tuples. INSERT records genuine initial state. No agency sweep, manufactured history, automatic initial seed or legacy data adoption.

Use narrow INSERT/UPDATE triggers on these exact financial tuples to prevent any current or future raw service patch from escaping the receipt contract. Prefer transaction-end/deferred receipt emission, or a proved final producer tail, so the clock is acquired after **all** business locks. A plain clock-taking AFTER ROW trigger is acceptable only after proving that every later trigger/owning routine in that transaction takes no WORK/revision/case lock. Alphabetical trigger names alone do not establish this proof. Do not allocate a command in a BEFORE trigger, then let the UPDATE or a caller acquire business rows afterwards. A deferred design must handle multiple same-row changes in one transaction explicitly and preserve a finite, exact mutation identity; do not silently coalesce away evidence. Any same-transaction accepted Enqueue must flush/verify pending financial receipts before choosing its sequence.

The module state branch must be explicit: factual Candidate/Umbrella administration continues under LEGACY/DISABLED without creating a NEXT financial job; NEXT emits the participating receipt using the existing clock and actual epoch. An unsupported/unversioned state must prevent affected Draft acceptance rather than fall back to today's settings.

## Lock order and enrollment contract

`1430 publish_staged_revision_v1` explicitly locks module → WORK FOR UPDATE → exact revision FOR UPDATE → retention/business witnesses, changes/seals rows, then **1404 receive_command last**. Preserve WORK → revision → clock. Candidate/umbrella/policy/source business-owner locks must also precede clock; do not hold agency clock while trying to lock selected input rows. Existing Source query global admission lock is earlier than all business locks, not relocated to the clock position.

At accepted SEAL_ENQUEUE, lock only exact selected Candidate/Umbrella/policy/query/case/work inputs in the agreed owner order, retain typed versions/evidence including genuine before images for a pending earlier producer, then allocate PREPARE and accepted_input/effective-work children atomically. Locks which would contradict existing publication order need a specific reordering proof or typed refusal; a generic advisory lock does not cure inverted row locks. No browser refresh, new wall-clock cutoff or whole-history reconstruction.

Any new metadata command kind must have explicit bounded enrollment behavior in the final `bpay_next_enroll_one_v1` successor: exact immutable receipt/digest/module epoch, finite membership, no financial job, advance enrollment clock without skipping real earlier jobs. Simply call `receive_command` from a trigger and leave generic enrollment unchanged is incomplete and can strand the agency clock. PREPARE Candidate members must already exist for accepted_input FK at Enqueue, and later enrollment must reuse them rather than insert duplicates (see companion F-25 design).

F-25 is complete only when every named producer and reader has genuine ordered immutable evidence. Uncovered qualified WAIT/Source, dedicated pay-method, future rule/status or mixed transaction paths must remain explicitly unbound/refused at acceptance, not silently be called frozen. F-26 resume/epoch is separate. All conclusions here are source evidence only, not runtime acceptance or permission for a fixture/testing programme.
