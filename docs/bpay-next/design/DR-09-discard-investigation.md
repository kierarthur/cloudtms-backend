## Smallest separately typed whole-run path

The card-named successor needs an immutable root discard request and finite Candidate-member release binding, with private ACL/FKs/guards and native seek indexes. These are the minimum durable support for the expressly named whole-run operation, rather than browser all-Candidate arrays or a new generic cancellation framework. Root records the original PREPARE command, run, authenticated discard actor, exact accepted root revision/selection/page/Candidate counts, optional bounded reason, ordered discard command and maintained enrolled/removed/blocked/completed counts. Each member records its native Candidate/member_no, original/active PREPARE jobs, current worker (nullable before creation), economic versus execution revision, Case selection/state, exact captured counts, financial release seeks/checkpoint and bounded projection/pending-origin continuation. Keep original run actor and immutable rows unchanged. Whole-run discard needs no new worker execution revision or replacement `active_prepare_job_id`: preserve both current and economic identity in its typed binding and use its own native job lease. The worker-execution guard need not change solely for this operation.

Use the card input `expected_preparation_revision` as a fence over the existing run `review_revision`; do not invent a second root revision. Permit0 because an early running preparation can have review_revision0. Expose this exact hidden operand through the existing PROGRESS read as required for this card, and compare it under the run header UPDATE lock before receiving a new discard command. Increment the existing root revision once on accepted discard to invalidate stale confirmation/child completion. Exact same-command replay checks immutable run/actor/revision/reason before fresh eligibility; a genuinely empty scope returns a closed no-acceptance/no-money result, rather than minting a dummy job. Distinguish an already accepted positive CREATE descriptor whose original PREPARE is still RECEIVED/OPEN and has not materialised selection counts: zero enrolled/selected_candidate_count alone is not empty. Its narrowly proved zero-member/no-job/no-worker retirement at0559:6394–6435 is metadata cancellation of an accepted preparation, not the genuine empty no-op.

Accept only the existing authenticated owner and an unconfirmed PREPARING/REVIEW run. Confirmation/expiry/discard serialize on that same header lock: a confirmed/expiry-won run refuses, and discard acceptance fences new child capture/completion. The ordinary due-expiry admission, receipt/table shape and72h Confirm fence remain unchanged. An already-accepted unfinished typed WORKER_RELEASE should finish its bounded cleanup/projection before whole-run discard admission, analogous to the existing expiry pending-release deferral (`0559:6392–6393`); never retire halfway through release, reset its money cursor, or double-count its completed exclusion. Exact original/active REPREPARE jobs can be retired under the new discard scope because their retained ACTIVE prefix is the cleanup source; preserve their captured checkpoints/history.

Enrol one original selection_candidate member at a time, capturing and retiring the exact partial original/current execution before taking over its Candidate lane. Handle the accepted-but-not-yet-enrolled original PREPARE receipt with the same narrowly proved zero-member/no-job/no-worker distinction as0559:6394–6435, and let a partially ENROLLING original command finish only through a discard-qualified native retirement receipt. Do not require original worker READY or job DONE for whole-run discard. Do not discover fresh Work or Cases. Claims use fresh native owner epoch/nonce, exact discard binding and original per-Candidate order; never adopt a live lease.

The shared release scope needs one new explicit PREPARATION_DISCARD branch proving its own request/worker/job/module/lease/revision/count tuple and no realisation/NET/transfers. Keep the original PREPARE worker-release and PREPARATION_EXPIRY due branches intact. The same CASE helper needs a discard binding selector and a discard-qualified collection reconciliation path; native collection scope/write guards and weekly exclusion need only that exact typed branch. The current expiry/pay-run guard also rejects any CANCELLING transition without an expiry request, so its root-header branch needs a separately qualified discard alternative; adding a second trigger alone cannot bypass the existing guard. No expiry deadline is borrowed as discard admission.
