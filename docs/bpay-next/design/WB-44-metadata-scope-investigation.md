# WB-44 metadata scope and actual producer seams

10 October 2026. Independent source-only investigation. Read the full WB-44 card, all thirteen child rows, W11/W12/W14, R2 section 5, Rule-B owner design, the current registry, native metadata/writer definitions and the proposed WB-44 producer/seed design. No SQL, runtime, tests, hosted reads, fixtures or product edits were performed.

## Scope conclusion

Candidate name/reference, current channel/Umbrella and genuine bank-warning metadata are required early WB-44 coverage. They cannot all be deferred to EX-08 or WB-29: W11 explicitly requires bounded name/channel/bank-warning fanout, and the card explicitly names Candidate name/ref/channel/Umbrella/bank warning and trigger coverage (`02_WORKBENCH.md:47,1567–1569`). Conversely, this does not authorize a current-settings earnings calculator, Source query evidence producer, accepted-input resolver, new financial command or replacement of the parked F-25 protocol.

The smallest correct distinction is between maintaining current projection metadata/control invalidation now and implementing the actual financial channel-change/restructure/rate-resolution operation at its later named owner. WB-44 must not mutate accepted Rule-B selection, run-worker target, expected revision, query snapshot or PIN. It must not infer a new payable amount from current channel, Umbrella VAT, finance window or Contract rates. EX-08, FC-13, WB-29/WB-32 and the CM owners retain those financial obligations at their actual build turns. R2 section 5 explicitly leaves later transition hooks to their owners; a broad finance-window/Contract settings census is not an instruction to rewire them in this early card.

Rule-B's text is a replacement for the F-25 build, not an alternate WB-44 completeness contract. Its prohibition on producer changes remains binding against settings versions, INPUT_VERSION/QUERY_INPUT_VERSION, certificates, producer transactions, deferred flushes and Source/query hooks. A narrowly named WB-44 projection metadata callback must retain only actual current operands and the projection pending generation; it must not recreate those parked mechanisms under a new name.

## Required boundedness and barriers

Candidate name/ref/warning propagation can use the real `(candidate_id,group_key)` index (`1252` migration:64) and maintained current group/item/summary rows. Channel/control continuation must include both current relevant Work and Case identities, retain old natural scopes before replacement and adopt the metadata generation only after every indexed page. No public Timesheet history or Candidate ledger discovery.

Umbrella changes are a genuine high-fanout case. Persist one exact Umbrella-scope task and a global pending barrier in the mutation transaction, before walking Candidates. Otherwise a Candidate outside the first page may still be offered from stale Ready state. Page actual current `candidates.umbrella_id` identities using a native UUID cursor and checked supporting index; then each Candidate's current groups. Retain generation/upper fence/cursor/visited counts. A Candidate moving into or out of that Umbrella concurrently must independently enter its Candidate callback barrier. No unbounded `array_agg`/loop, arbitrary first100/500 completion or global financial refresh.

Warning semantics remain the existing WB-08 definition: NULL clears; MISSING is actual missing normalized native hash; CHANGED is a genuine saved identity change. These are factual warning metadata, not bank verification, payment readiness or a basis for replacing the approved source. Seed can prove MISSING from the actual current NULL hash, but cannot invent CHANGED from an assumed historical identity. A name-only Candidate change that leaves the normalized bank identity unchanged must not create a bank warning. Umbrella name can genuinely change its native bank hash because that name is the existing holder identity.

Page work must prehold the complete sorted Candidate/Work/Case set before task, metadata and singleton revision locks, then revalidate task generation/cursor. Do not lock a task/global singleton and acquire a new Candidate afterward. The existing name callback already acquires Candidate control after the public mutation row; a larger replacement needs an actual finite lock-order review, not a claim that AFTER triggers are automatically safe. Avoid added public Candidate/Umbrella row locks in reverse order inside projection consumers.

Current `WB-44-producer-seed-barrier.md` correctly separates metadata continuation, linked-Case fanout and financial owners, and now names OPEN/PAUSED Case seed, existing-group reconciliation, own-seed pending exclusion and Candidate-before-task ordering. Its metadata census caveat must be resolved into the concrete Candidate field list and Umbrella attachment disposition above before whole-card completion. The same-generation completion must pin all control operands, including NULL/unknown channel; no older task may clear a newer metadata pending flag or singleton count.
