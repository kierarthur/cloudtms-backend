# WB-29 W2 receipt and publication investigation

12 October 2026. Read-only continuation under BD154/BD155 and WB29 card/checklist. No product, SQL execution, hosted/business call, test, fixture or screen action. This note defines the smallest native receipt support; it is not implementation or runtime approval.

## Recommendation

Add only `RESOLUTION_SAVE` / `RESOLUTION_CLEAR` to the existing W2 action dispatcher and its closed Worker contract. Those are W2 intent actions, **not new Worker command/job kinds**. A changed Work publishes through the existing `POSITION_APPLY` command. Reuse `private.bpay_next_workbench_command_receipt` with a narrowly discriminated resolution receipt variant. Keep WB45's decision/event tables as the sole decision store.

WB45 rows alone cannot give complete exact CLEAR/many-Work replay: a CLEARED event retains command/actor/reason but not the full original request/result, and an empty/idempotent clear has no new event. The original command row retains sequence/epoch/kind/status, but not actor/request. The existing workbench receipt supplies those missing facts without another decision store.

## Concrete small receipt variant

Add one closed action discriminator to the existing workbench receipt, with historical/default `RETRY_WORK_JOB` preserving its existing semantics. For resolution-only variants allow job_id NULL and no retry-execution fields; one-Candidate request qualification remains exact. A many-Work result may use work_id NULL only under that explicit resolution variant, with a nonempty bounded original Work set in request/result. Single-Work retains its actual ID. Keep original retry branch's Work/PREPARE and five-field constraints byte-equivalent within its discriminator. Do not use a fake job ID or drop all NULL guards.

Retain exact original `args`, actor and module epoch in the receipt. Put actual native child publication IDs/revisions/sequences and saved/cleared decision IDs/versions in the bounded result. A result-only parent request_id need not become a Worker command; the child IDs are real POSITION_APPLY commands. Use the original request UUID as the first native child's ID when suitable, and server-generated child IDs for other Works retained in the same immutable result. A no-change/empty clear has only a native W2 receipt and no invented economic command.

Use existing 4KiB request /8KiB result limits unless a concrete card-required need demands an action-specific bounded extension. Declare explicit component/Work count bounds (no greater than the existing100-member bounded control/refresh envelope) in addition to bytes, reject duplicates, mixed Candidate identities and ambiguous linked sets, and refuse oversized complete-publication payloads rather than truncating. The complete accepted Work set must be supplied/qualified finitely; do not add a Candidate/agency history discovery sweep or new MANY protocol.

A minimal closed SAVE row names actual Work, expected current revision, approved line, rate family/code, expected decision/version or explicit none, native current context/control signature, selected mode, exactly its applicable manual-rate or manual-amount string, and reason. Common original request carries request_id, Candidate, module epoch, actual target channel/Umbrella/VAT, policy/date and the explicit finite rows/context. CLEAR names exact existing decision ID/version plus its Work/current boundary identity and reason; the receipt retains these operands even though WB45's CLEARED event must refer to the old decision's based-on revision/approved line.

Suggested result structure is an exact received/replay envelope plus rows of actual changed Work/published revision/child command/agency sequence and decision ID/version outcomes, or an explicit no_change result. No estimate, rate/units, successful publication, actor or revision is guessed. Exact saved result is returned on unknown recovery; do not rebuild it from current ACTIVE rows.

## Replay and fresh mutation ordering

1. Retain original public service role/admin/NEXT admission. Validate only finite exact request syntax and original owner epoch needed for identity. Read the native request receipt before current Work revision/control/rate checks; compare exact actor/action/original args/receipt epoch. Changed-body reuse refuses. Same accepted request returns the stored result even after a later save/clear or revision change. Original epoch checks must not silently adopt a new NEXT activation.
2. Readback with no original receipt returns received=false and performs no publication, decision/event mutation or command-clock allocation. A matching command without the W2 receipt is not proof of this actor's request.
3. For a fresh request, discover the explicit finite Work set and genuine related collection Case IDs, then prelock all Candidate controls in native order and **all Work parents in UUID order before the first Source seed or Case refresh**. Prelock the bounded related Cases before a seed can invoke its existing Work/Case refresh path. Lock/qualify exact relevant Position/native financial evidence after these parents, preserving original order.
4. Recheck the original receipt after serialization. Then freshly qualify every requested expected revision/current/applied/physical identity, target/Umbrella/policy/date, independent mode/bucket/basis and expected active decision/version. A fresh stale request returns the named stale refusal without silently refreshing or changing its body. Latest E2/BD019 changed-revision holds/releases remain intact.
5. Source UNBOUND seeding uses the existing owner while the genuine predecessor is still current/applied; READY books are not reset/reseeded. Current source seed1309 itself calls Work refresh after Position update. Do not acquire Work2 after Work1's Case refresh or after the first child's command clock. The finite prelock requirement is essential even when every Work belongs to one Candidate.
6. Stage complete native treatment revisions through BD155's exact root/payload assertion and original publisher. All existing related metadata/financial/FK parents required by subsequent children must already be qualified/held before the first command-clock acquisition. No fresh scope admission may occur after that clock.
7. Each changed Work publishes once with its own retained POSITION_APPLY child command. Multiple requested buckets on that Work share that one complete revision/publication. No partial approved revision, fake financial command, repeated publication for every bucket or current approval repricing.
8. Insert the immutable workbench request/result receipt in the same transaction after all native child outputs are known. Any error rolls back every staged revision/decision/event/child command/result. Small one/many-Work W2 should be atomic rather than importing snooze's partial-child retry machinery. Future large linked UI owners can reuse explicit closed original requests; this does not authorise a new bulk protocol now.

## Mandatory decision/event order

CLEAR: qualify/retain and lock the exact ACTIVE decision, stage/publish the complete Work through the original publisher so the actual clearing POSITION_APPLY command and Candidate member exist, then INSERT its CLEARED event with the old based-on revision/approved line/family/code/decision/version and that actual child command/actor/reason, then UPDATE only state to CLEARED. The event's immediate command/Candidate FK requires this publication/member before event insertion. Event guard2100:152–157 requires ACTIVE during insertion; decision guard70–75 requires the event before state UPDATE. Deferred audit163–184 proves both sides at commit. All steps are one transaction; reversing either required order fails native guards.

SAVE replacing an existing active identity: qualify/snapshot old versions and new operands under original locks, stage/publish the complete target treatment first to establish the child command/Candidate member, clear old event→state, INSERT the new immutable version with both original/current and published mapping/basis plus that actual publication command/member, then INSERT SAVED. Deferred audit requires SAVED for every new version. Never insert ACTIVE over the existing unique-active identity or later mutate publication mapping (guard permits only state change).

BD155 sibling carry is also explicit new versions, not UPDATE of old selected operands/mapping. After the shared Work publication establishes its native command/member, clear each old sibling with event→state; carry only exact compatible immutable basis/selected operands/reason and qualified save-time residual. A manual-amount residual drift must refuse rather than refresh its old amount/basis. Resolve replacements and carries once per complete Work publication, with monotone version under original Work lock. Existing event_request_idx2044:100–102 allows only one event per (child command,event kind,approved line,family,code); validate the finite set has no collision. One current-qualified version per bucket fits. Multiple target-specific versions of the same old line/bucket cannot be silently grouped into one CLEAR child or admitted by dropping that uniqueness.

CLEAR event must not use a published line merely because it is currently shown: its immediate guard compares the referenced decision's based_on revision/approved line. Preserve these two identities distinctly in the original request/retained result.
