## Scope and concrete recommendation

Use a **separate private Workbench metadata task**, transported by the existing queue and background/minute entry, with its own narrow service-only SQL lane. Do not manufacture a financial command or relabel a POSITION_APPLY/PREPARE job as a metadata job. WB-44 explicitly names bounded metadata jobs/leases/progress and current seed; it does not name a new financial command protocol. The existing command clock, enrolment owners, public financial service0280 and parked F25 owners can remain unchanged.

This recommendation is based on actual schema:1324:967–991 requires every `private.bpay_next_job` to have a non-null command_id/sequence/Candidate, compound command and command-member FKs, and unique(command_id,candidate_id,job_kind). Its financial Candidate ordering index is at1063–1065. Current1430 position CLAIM397–450 checks the actual POSITION_APPLY kind, module epoch, status/lease and every earlier unfinished Candidate command, then increments the **financial** worker-control active_owner_epoch. Current Worker kinds, phase schemas and0280 dispatch are closed. Seed/name propagation has no genuine POSITION command/member to attach to, and borrowing the financial owner epoch would invalidate an actual financial lease. Extending POSITION_APPLY with a projection phase also cannot solve name propagation or initial seed independently.

The private metadata task should use the existing module owner epoch and Candidate control lock for exclusion, but a **task-local** lease owner epoch/nonce. It must never increment financial active_owner_epoch, allocate agency_sequence, insert command/member, or add enroller/0280 switches. A new finite internal task discriminator/service action is metadata support explicitly required by this card; it is not a public business command or Create protocol. Do not expose it to Office or add a new HTTP business route.

## Minimal private task support and replay obligations

Suggested additive task fields (names are design suggestions, not existing installed objects): task UUID; finite purpose covering current seed, existing Candidate metadata propagation and exact WORK/linked-Case reconciliation; exact Candidate/WORK IDs where applicable; immutable target generation using existing adoption_revision/metadata_version or actual work revision and financial revision; module epoch; phase and native keyset cursor(s); READY/LEASED/pending-or-error/DONE status; task-local owner epoch, fresh nonce and DB-clock lease deadline; indexed wake_after/available time; bounded fixed error code; finite rows/progress and last completed page identity/reply. Task uniqueness must deduplicate **the same actual scope/version**, not suppress a later version.

No generic financial snapshot, request digest, source certificate, new agency clock or full-row settings journal is needed. The task's progress is an actual metadata completion receipt. Keep native FKs/owner/private RLS and browser/service table revokes as in1252; only the small SQL service wrapper receives service_role execution and independently verifies JWT role and active NEXT/module epoch.

Use the existing scoped CLAIM/STEP principles, adapted to this private task rather than calling the financial owners:

- Fresh CLAIM locks Candidate control before its task row; only READY or actual expired lease qualifies. Generate a fresh task nonce/local epoch, never expose/adopt another active claim. Seed discovery can plain-read its bounded next identities first, then lock sorted Candidate controls and revalidate the task cursor/claim before touching projection rows. No producer should acquire a seed-task lock after taking the global projection revision.
- STEP validates exact persisted scope/generation/module/lease/page identity and expected cursor. Candidate control precedes exact WORK/Case, metadata and singleton projection revision. Page limits and total visited/update rows are at most100; nested children must not silently turn100 groups into10,000 updates.
- Cursor mismatch/duplicate reads the real stored completion/progress and performs no second replacement. Lost CLAIM reply waits for lease expiry, rather than recovering an exposed active token. Lost STEP reply retains the same exact task/page identity. A last-reply cache alone only covers the last page: if arbitrarily delayed older deliveries must be acknowledged, either retain their narrow real page receipt or prove from that task's immutable generation/cursor that the exact page is complete. Do not claim an unknown/missing task or different generation completed.
- A new native/metadata version arriving during pages leaves pending true and creates/requests its own actual newer generation or safely resets the exact task under Candidate control. An older completion cannot clear the newer marker. Error completion remains explicit and cannot decrement dirty counts into CURRENT.
- Wake-page discovery is a separate bounded due index for READY and actual lease-expired tasks, with persisted rotation as0560 does for financial wakes. It does not take over a lease. Failed enqueue or crashed Worker is recoverable from the task row; queue delivery is never the authority for projection completion.

An IDs-only queue can reference a persisted step identity whose stored task-local claim/cursor it exactly names. Resolving that identity under the service/task guard is not permission to look up and adopt an arbitrary latest nonce. This is the finite task receipt/lease support named by WB-44, not a new business command protocol. Final implementation must choose and close that actual transport contract; existing financial reply schemas are not an implicit metadata interface.

## Initial current-scope seed and concurrent barrier

Reuse existing1252 singleton `bpay_next_workbench_revision` fields: adoption_state UNSEEDED/SEEDING/CURRENT/ERROR, adoption_revision and dirty counts (migration6–15). No current source consumes its initial seed. Start the explicit private seed independently of any Workbench UI/F19 adoption. For a clean empty launch it must legitimately finish an empty current scope and record CURRENT; ZERO Source books are not seed membership.

Discover only current relevant native WORKs and current open Case scope. WORK is already one native identity per booking; do not visit work revisions, Timesheet version families or agency financial history to discover members. Approved and genuinely withdrawn retained WORKs are the declared scope; classify them using1410/1321 rather than guessing money. Native Case status values are OPEN/PAUSED/CLOSED/WRITTEN_OFF (1324:355–370), not a guessed CURRENT enum. The exact seed predicate must explicitly say which current nonterminal Case rows require presentation; OPEN is named, and any PAUSED row retained as a current classified Case must not disappear through a fabricated terminal interpretation. Closed historical Cases are not a history seed fallback.

Use native UUID keysets, persisted phase/last key and a fixed initial upper key/scope generation. Capture upper UUID by ORDER BY id DESC LIMIT1, not max(uuid). Add only the current-relevance partial indexes needed for WORK/Case ordered discovery; existing candidate/week Work index1324:994–1000 and Candidate Case indexes1017–1020 do not by themselves prove efficient global seed keysets. No OFFSET or first500 completion. Each page persists its receipt/cursor in the same transaction as exact group/summary replacements. Reuse the existing item/group/delta arithmetic; do not define a second projection.

An upper-key fence alone is insufficient: a concurrent new UUID can fall behind the cursor. The existing early publisher/withdrawal paths must enter the **same durable dirty/task barrier** in their transaction. Common publisher1346 already marks exact Processing before its agency clock; ordinary and Source withdrawals1332 already refresh exact current work. Attach only the minimal private task request/dirty continuation to those named seams, preserving the actual Source/protected owner→stage→pair→publisher paths. Every post-start creation/current change is represented even if below the seed cursor. There is no new public catch-all trigger or late Source/query producer patch.

At the final seed step, under the real projection/control locks, require completed native keysets, reconciled actual groups/items/natural summaries/counts and no unresolved older/current dirty task/version. Then advance adoption token/CURRENT once. A newer publication, pending position apply, metadata version or unfinished linked-Case task prevents read enablement or leaves truthful pending. Missing native facts can be an explicit nonselectable unknown/Blocked contribution; they cannot be silently omitted or manufactured zero. CURRENT means a coherent current projection, not that every row is payable. A genuine native-conservation failure remains ERROR/pending.

WB-09 and DR-02 must consume this actual server-side current/pending/error/token boundary; no client/session flag bypass. They are later consumers, not prerequisites for building/seeding this state. Do not require optional F19 adoption or let first list/Draft initiate an agency sweep.

## Existing Candidate metadata fanout: copy facts, do not revalue

Current1252 name/ref trigger682–701 and bank-warning owner662–679 already update candidate metadata_version, continuation_pending and singleton dirty_candidate_count only on a genuine change. The pending partial index exists at migration29–30. Add a task request to these existing named callback seams, not another public trigger. The task must consume their real current version under Candidate control.

Use bounded native/current projection keysets for existing Candidate groups/items and natural candidate-summary rows. Copy only authoritative display name/ref/bank-warning/metadata version and required coherent revision fields. Reuse stored amounts, Source channel and actual contribution vectors; never call a rate resolver, recompute earnings/headroom, scan Candidate payment history or reinterpret accepted Drafts as part of name propagation. If a metadata change genuinely alters natural scope, use existing before/after apply_delta with **stored** contributions, not a second calculator.

The current item candidate index is `(candidate_id,section,group_key,component_key,member_kind,member_key,portion_kind)` (1252 migration177). Use its actual tuple or add a narrow `(candidate_id,id)` continuation index; do not assert `WHERE candidate_id AND id>cursor ORDER BY id` is covered by that different ordering. Group Candidate index64 and summary natural keys supply other finite phases. Advance adopted_metadata_version and clear continuation_pending/decrement dirty_candidate_count only after **all** affected phases for that exact unchanged metadata_version complete. If the version changed, restart/continue the newer actual version, leave pending and never publish an old display as adopted. Do not update100 groups and call a large Candidate complete.

Channel/Umbrella/rate/finance-window mutation is not established by the existing name/ref trigger. This design does not add those prohibited broad public/settings triggers or claim their later producer hooks built. List actual named later owners in the maintained census rather than certifying a field merely because it appears in the card's superseded late-producer inventory.

## Greater-than100 exact linked Cases

Current1346 refresh_many80–93 discovers at most101 and **refuses** total>100, so current final position transaction cannot succeed for a large linked set. Current1410 WAIT prelock44–49 and final Case loop323–326 are unbounded. Raising the limit, dropping the extra Cases or calling first100 complete is incorrect.

Keep the existing small atomic path. For actual high fanout, a private WORK/linked-Case task must retain the exact native WORK identity/revision/financial version and the genuine WAIT-before/after transition. Native1519 `work_collection` has unique(case_id), unique(work_id,component_key), and its Candidate index `(candidate_id,work_id,component_key)`; it does **not** supply an ordered `(work_id,case_id)` continuation index. Add that narrow index for exact unique linked-Case keysets. The newly saved1429 migration already names `bpay_next_workbench_origin_case_page_idx` on `(work_id,case_id)`; this is a source observation of that index, not a review or installation verdict for the new batch. Per page acquire same Candidate control, at most100 exact Case locks, then existing Case contribution owner. Keep Candidate/work projection pending/Processing and retain its dirty contribution barrier throughout **all** Case pages. Intermediate summaries may be physically updated, but cannot become a client/current/Create baseline while that generation is pending.

At the final Case cursor, verify no remaining exact linked Case and unchanged actual native generation, then replace the final WORK contribution **once** and clear the matching pending marker atomically. A new lower-sorted Case membership/financial version during paging must force the new generation/restart, not disappear behind the cursor. Every future native link mutation must enter its own named later-card hook; no early FC/CM implementation is invented here.

Do not use a session/GUC boolean to skip1410's Case loop. A safe finite split is a private contribution-only core (same native calculations) plus the named refresh wrapper/task orchestration; only the genuine complete task phase may call the final core after its actual Case work. Alternatively a private task-bound final helper must verify its real lease/generation/completed cursor. There is one economics owner and one before/after delta, not copied competing Case calculations. The new worker cannot call `refresh_many` recursively to evade its100 cap.

The financial position job's own APPLIED/DONE receipt and the metadata projection's CURRENT receipt are different authorities. Existing1346 writes native terminal status before refreshing, but its transaction presently rolls back if large refresh refuses. A successor may atomically retain native application plus a durable dirty metadata handoff; it must then keep the actual read/Create barrier pending until linked Cases and final WORK finish. It must **not** claim that financial DONE means Workbench CURRENT or clear pending early. If the requirement is instead to withhold even the native job/command COMPLETE until all projection pages finish, that needs a POSITION phase/CLAIM/STEP/service-contract successor and would broaden the financial lane; it is a cost of that option, not safely achieved by just adding a metadata table. Under the binding scope guard, the separate metadata receipt/read barrier is the narrower option.
