## Concrete native constraints that a design must resolve

1. **Cut reservation is not upload acknowledgment.** Create1832:469–473 already inserts real run_selection/work_choice for every eligible accepted Work, including ALL and SUBSET; skipped attempted Works still have immutable run_choice_member. Literal NOT EXISTS(work_choice) matching would suppress the entire accepted set. Conversely blindly acknowledging SUBSET in MATCHING would violate the required SUBSETS→EXCLUSIONS→MATCHING seven-phase order. Distinguish accepted reservation from an uploaded/materialized member. MATCHING must skip already uploaded SUBSET choices without converting them to ALL, not skip unuploaded precreated ALL choices.
2. **Current ACK is a contiguous prefix.** 1832:602 requires member_no=uploaded_choice_work_count+pageIndex;614 requires selection_no=uploaded_selection_count+acceptedIndex+1. Uploading subsets first when their immutable member numbers are interspersed with ALL cannot satisfy this. Counts cannot be repurposed as a seek cursor after out-of-order ACK. Existing seal885–887 compares aggregate uploaded counts and all attempted membership/exclusion rows; preserve exact-once totals while changing only the necessary metadata proof.
3. **Empty receipts are currently rejected.** ACK557 and core1324:442–447 constrain selection-page rows/item_count to1–100. R2-F06 explicitly requires empty exclusion receipts; card913/234 requires immutable empty and only-skipped matching pages. Empty requests must have real replay/conflict authority, not a synthetic complete result. An all-skipped nonempty page already has attempted IDs plus genuine skipped_json and remains distinct from a zero-member page.
4. **Exclusions are already fixed at Create.** Create330–337 writes Candidate exclusions first in UUID order then Work exclusions with a shared100-size ordinal/page_no convention. Once descriptor is installed, guard36–37 rejects new exclusion/member insertion. EXCLUSION_PAGE must validate/acknowledge exactly that accepted set, including original page assignment, not introduce later exclusion choices. Its separate existing request_json relation permits a zero-ID body.
5. **Zero exclusions need one explicit convention.** Existing seal887 requires exclusion_page_count=ceil(actual exclusion rows/100). Recording a required empty exclusion page1 and incrementing to1 fails the unchanged zero-set check. Choose a compatible explicit empty acknowledgment rule (for example one empty page when zero rows, max(1,ceil(n/100)) completeness for descriptor runs only), with no alteration to legacy non-descriptor semantics. Don't silently discard the receipt or pretend no page was received.
6. **Closure cannot be inferred from any selection page.** Required subsets precede exclusions; ordinary SUBSET acknowledgment pages may therefore exist before the first MATCHING_PAGE. EXCLUSION_PAGE must close only at the first actual matching receipt or seal, not merely selection_page_count>0. Exact old page replay should precede fresh-open/closed checks.

## Minimal support options for root's decision

Preferred metadata option: one nullable `acknowledged_page_no` on each accepted WORK member (or equivalent uploaded flag with an actual page reference), plus a native matching cursor in retained member_no order. NULL means captured, not uploaded; a non-NULL value names the immutable actual original selection-page receipt. This permits original WORK_PAGE SUBSET acknowledgment before matching without changing accepted Work/revision/mode/selected/skip facts. Under the existing module/actor/run lock, validate native Work identity and exact expected revision/mode, require unacknowledged member, append the real page receipt, acknowledge once and update actual attempted/selected counts once. Duplicate same page replays; a Work on a different page refuses. Don't rebuild a choice, renumber run_selection, change selected money or let boolean acknowledgment masquerade as a page receipt.

Necessary guard implications are finite: existing accepted_choice_guard25–31 currently forbids every accepted member UPDATE. A successor may allow only NULL→actual page reference for WORK while every original accepted semantic field remains byte/typed-equal and the exact page contains that Work. No DELETE/TRUNCATE/semantic update relaxation. Existing exclusion/member immutable behavior remains. A partial seek index such as (run_id,member_kind,member_no) on unacknowledged members supports the finite native walk; exclusion page lookup can use a small (run_id,page_no) index if needed. No public trigger or financial command changes.

Alternative is separate acknowledgments in the existing immutable selection_page receipt/body: prove native member coverage from actual pages and use a compact maintained cursor/count. It must still distinguish reservation from upload, support efficient exact lookup and no duplicates, and not rescan every earlier page for each matching request. Reuse existing storage where it is sufficient; adding only the indispensable member/page metadata is smaller than a parallel manifest/proof framework.

Matching control request/cursor and complete outcome must be retained exactly, including empty pages. Existing `choices_request_json` records only the original choice array; it does not retain an independent matching cursor/filter request. A narrow optional matching-request/outcome field on the existing page receipt is one option. Its immutable guard/INSERT path and0–100 constraints must be adapted coherently rather than overwriting an original immutable receipt after append. Keep every legacy non-descriptor restriction unchanged. The design decision belongs to root; no schema is authored by this note.

Once accepted SUBSET uploads are genuinely acknowledged/sealed, MATCHING_PAGE walks only native accepted ALL/unacknowledged members, at most100 raw members per request with a deterministic member_no final identity. It acknowledges actual prior exclusion/subset dispositions without creating an ALL choice; a page containing only skipped Work still advances the true native cursor and preserves skip receipts. Empty terminal page has an immutable input/outcome and does not create a financial job. Never walk current CANDIDATES/GROUPS/EXPORT_ROWS or name/amount keys after Create. No new Candidate admission, rates, channel, holds or query evaluation occurs in enumeration.

## Fresh exact-ordinal correction before BD076 implementation

The earlier section2 statement that SUBSET members may be interspersed is incorrect. Exact Create1832:353 is `row_number() over(order by (coalesce(ov.value->>'mode','ALL')='SUBSET') desc,i.work_id)`: all SUBSET members are already a leading UUID-ordered prefix. The prior note inferred the order from an incomplete read; this correction supersedes that inference. No product source changed.

Thus mandatory SUBSETS→EXCLUSIONS→MATCHING can retain the current contiguous ACK if the sequencer enumerates the original immutable prefix (including captured subset skips), completes eligible subset component seals, then ALL matching starts from the existing uploaded_choice_work_count. A new per-member acknowledgment flag/FK is only justified if an actual required caller must submit that prefix out of order. The card does not itself require arbitrary subset ordering. The design review records the smaller exact variant and required empty receipt/exclusion closure work.
