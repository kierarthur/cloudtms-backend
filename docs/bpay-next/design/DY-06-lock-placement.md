## Why the exact Work lock is required

Accepted Create (`11102026_0426_banking_pay_next_pay_hold_accepted_choice_v1.sql:292–305`) takes native Work/revision SHARE locks before copying accepted membership. It writes `run_selection` and immutable expected-revision `work_choice` at 578–582, including SUBSET OPEN, before acknowledgement; native choice INSERT also takes exact Work SHARE at 26. There may be no run line yet. Current route wrappers lock Timesheets/TF/workflows but not Work. A plain context EXISTS therefore can see no choice and then rotate while Create commits a choice.

Use the existing unique native Work for the locked current booking and a **conflicting row lock**, such as `FOR UPDATE NOWAIT`. SHARE does not conflict with Create SHARE. The lock is retained through the whole transaction. A failed NOWAIT must abort/refuse; it must never continue without the lock or use a guessed/stale Work. A successful lock followed by a fresh context/predicate statement gives the required READ COMMITTED ordering: earlier accepted Create is visible and refused; later Create must wait until rotation finishes and then requalify its native current offer. The correct withdrawal already takes Work UPDATE (`0939:883–888`) and needs no added lifecycle protocol.

## Direct dispatcher placement and retained refusals

The real direct Daily Worker call is `broker/src/index.js:105420–105425`; it reaches the same public dispatcher but can enter its dormant legacy branch. The native Office path uses `broker/src/candidate-app-backend.js:11109` ROUTE_CONFIRM and is covered by confirmed placement.

Add the same exact Work NOWAIT plus the narrowly shared **financial-only** predicate immediately before the existing legacy call at `0922:2299`, and before the core call at 2312 **after** the existing confirmation-GUC requirement at 2304–2310. Two calls to one narrow mutation support, or equivalent branch-preserving common code, are sufficient. Keep Source/import checks and permissions/feature branching first. Qualify the exact locked canonical current physical row against `p_expected_timesheet_id`, genuine DAILY, valid actor/input/action domain; leave missing/stale/unsupported inputs to their original body rather than allowing a new financial test to mask their original validation outcome. Keep non-NEXT and unrelated scope behavior unchanged.

Do **not** call the full current route context and reject on its `permitted_action` in the flag-off legacy branch. The full context also reads coordinated Candidate paper/workflow, restore proof and row signature and can introduce new refusal behavior into the preserved legacy route. Share only the card-required native financial-retention classification between the private context and wrapper assertion. The smallest justified support is one private closed predicate over exact native booking/Work/physical facts; it is not a new command, storage framework, money formula or public reader. Its accepted-membership lookup should use the necessary private `(work_id,run_id)` Work-choice index described in the main investigation. Retain every native financial blocker and the sticky Archive marker; approval-only marker by itself is not financial retention.

Re-entry from confirmed is safe: confirmed retains the same Work lock; dispatcher re-taking it is re-entrant. Any later assertion failure rolls back the whole original confirmed transaction. Do not remove its original private-core auth/scope/route/import validation after adding the wrapper fence.
