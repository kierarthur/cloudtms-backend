# F-13 scope and checked implementation design

10 October 2026, after completed F-08. Read the full F-13 card and its three checklist rows before product edits. Exact named objects: D01 exact legacy/NEXT envelope classifier; D02 durable reconciled message-retirement receipt; D03 DLQ/transport-exhaustion procedure. Product boundary is the existing shared consumer in broker/src/index.js and one small supporting module for these exact objects. DB and Office: none. No new queue/configuration, SQL, commands, producers, money owners, certificate protocol or proof framework.

Option A is selected as the plan directs. Each message first receives fresh database ownership. DISABLED/LEGACY deliveries retain retry, including unexpected NEXT messages; no reverse activation policy is inferred. Under NEXT, existing exact metadata/financial adapters remain responsible for NEXT schemas and effects. Exact raw legacy families are recognized without their former coercion/defaulting parsers: operation v1, certificate continuation v8 and Workbench wake v1. Extra/missing/mixed fields, invalid numbers/UUIDs/timestamps/source-policy combinations remain unknown. Recognition alone cannot acknowledge.

Positive qualification must come from existing real native facts. The existing read-only pay_workbench_settled_certificate_status_v8(session,actor) can positively establish that the exact certificate build is SEALED_CURRENT, current-ready, ready-for-draft and not pending/recovery-required. Require its exact envelope certificate/session identity. This retires only a completed metadata build wake, without creating a Draft or implying payments completed. Operation qualification must bind its actual operation/type/batch/root and a real terminal/reconciled disposition; neither COMPLETE alone nor an omitted census row establishes all obligations. Workbench scope wakes with no positive exact native closure remain retained. Qualified families are extended only when the investigation demonstrates a real existing evidence owner; absence, empty categories or an owner flag cannot supply it.

D02 stores the bounded native qualification in existing public.audit_events, using an insert/read-only fixed service transport. The actual queue message's native 128-bit hex ID is represented directly as the audit UUID (no new digest or witness). Its complete native ID and closed retirement packet are verified against any existing row. Collisions or unsupported ID formats refuse and retain. The existing UUID primary key makes one permanent event for one queue message even on concurrent replay. No upsert/update/delete, generic swallowing audit helper, or financial status write is used. A successful response alone cannot acknowledge: verify the exact stored row on a fresh GET before ACK. Lost replies and conflicts retry through that same ID. The single durable event is the once-only bounded ID/reason log BPAY_NEXT_LEGACY_ENVELOPE_RETIRED; console delivery is not falsely promised exactly once across a crash.

The receipt omits payloads, lease text, financial/bank/provider data, actor contact and secrets. Native session/certificate/operation/batch IDs and closed disposition codes suffice. Replays still require current positive qualification. Consumer catches expose only closed reason codes and retain unknown or nonterminal work. One complete bounded deadline covers qualification, insert and verification, with capped response bytes and no redirect/fallback.

Handover question: could an acknowledged wake contain work the census did not see? The implementation never treats census absence as permission. Certificate acknowledgement requires the exact completed existing build; native financial/scope wakes require their own positively established disposition and otherwise remain retained. No unknown queue-only work is silently lost. Final release readiness still requires the separate F-18/F-19 disposition and external quiet-window evidence; this code does not claim it performed that handover.

Under DISABLED, messages can exhaust max_retries=10 into test-cloudtms-banking-pay-continuation-dlq. This is acceptable for NEXT only because durable job rows remain authoritative and F-11 READY/LEASE_EXPIRED/EXPIRY/ENROLL lanes rediscover eligible work; F-26 supplies separate epoch-validity handling. Real old obligations remain preserved for their approved owner disposition. D03 records that bounded procedure without executing queue, drain, provider or mail operations.

BUILDER DECISION BD022: use the narrow existing-status/read-plus-existing-audit implementation for F-13. Keep every unqualified legacy scope for reconciliation rather than inventing a global closure mechanism. The earlier external ticket/barrier/digest proposal is historical and is not imported. Native queue-ID conversion is a receipt primary key, not a new envelope/proof protocol. Cloudflare documents Message.id as a unique system-generated string; unsupported formats fail closed.
