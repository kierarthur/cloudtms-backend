## Chosen native page sizes and identities

Keep current PIN=one selected Work, capture/segment=100 combined native units, position hold=100, Case stage=100, Work/Case projection=100. Limit is a per-call page bound, never a Run Timesheet cap. Keep original job/candidate/command/epoch, lease nonce, phase and complete native cursor tuple at every call. A nonterminal page commits its own checkpoint and yields through the existing financial service; the next turn takes a fresh CLAIM. Original cut, Query admission, captured economic versus execution identity, native money locks and replay remain unchanged.

Keep current queue max_batch_size1/max_concurrency2/max_retries10. Accepted commands first retain their original durable wake. An unknown dispatch is never classified as complete or repeated with fresh economic inputs. Existing PF08 failure/backoff/attention and expiry/discard/release ownership remain untouched. Neither a browser count nor this design's arithmetic admits/refuses a payment.

## Budget without invented measurements

For N Candidates let W_i be selected native Works, R_i combined position/segment/recheck units, H_i run-position hold units, I_i Case instructions, A_i original Case selection members and V_i relevant prior-week contribution rows. Native page receipts, rather than Timesheet count alone, determine work. PIN costs W_i+1 calls. Capture/hold/projection costs include exact-bound exhaustion pages; a useful planning count is floor(R_i/100)+1, floor(H_i/100)+1, floor(W_i/100)+1 and floor(A_i/100)+1. Case finance adds its actual separate week/instruction/allocation stages; no-Case uses its original terminal call. Branches, retained binding work, errors, waiting and recovery can add calls; the expression is a planning approximation, not a universal upper-bound theorem.

Let S be actual financial STEP calls, E enrollment calls (currently N for the original PREPARE), L average native RPC latency and Q accumulated delivery/publication/lock delay. Queue-only operation needs approximately E+2S native RPCs because every delivery takes fresh CLAIM then STEP. With two consumers the optimistic serialized-work term is `(E+2S)*L/2`; Create upload/readback and Q must also fit60s under owner C3. Unequal per-Candidate chains and Source serialization can make the critical path worse.

Illustration only: 30 Candidates, 300 selected native Works evenly split, ten simple positions plus ten segments each, no Case instructions, no waiting/retry: PIN11 + capture1 + hold1 + no-Case1 + Work projection1 + empty Case projection1 =16 STEP/Candidate, S480 and E30, or990 RPCs. This is **not** the genuinely mixed 300-Timesheet acceptance population; expenses/other native Works or Case stages increase it.

| --- | --- |

The native timeout8s is not an expected latency. The owner-reported DB-only1.1s/1.8s is not a Worker/RPC latency sample. This sensitivity shows why no source-only60s PASS or claim that concurrency2 necessarily fails is justified.

## Smallest optional accepted-request drain

Root chose the bounded public enrollment page below because the exact card says database enrollment pages create all jobs in a few steps. That supersedes the initial Worker-only20-call interpretation. Use one finite ctx.waitUntil task after a positively accepted SEAL_ENQUEUE, preserving the accepted response even if the task fails. The current wake header also covers manual reprepare/release, discard and WAKE, so the header alone is not permission for a fresh Create drain: inspect the closed `response.clone().json()` action and require SEAL_ENQUEUE plus its accepted receipt. Preserve those other actions' original wake behavior. Reuse current enrollment/financial adapters and current ID-only wake/failure handling. Do not start a drain on choice uploads, reads, Preview, unknown acceptance or a refused command.

Recommended smallest database support: successor only to `public.bpay_next_enroll_service_v1()`, retaining private2041 unchanged. After its original first call, repeat that same owner at most20 total times only for the same original PREPARE command whose selection is SEALED, command ENROLLING and Run PREPARING, with no OFFICE worker-action request or expiry/discard fence. Stop before crossing the first command's sequence: once the clock advances, finish the page. Other commands retain one original call. The private owner still inserts one exact frozen Candidate member/job per iteration; the public page is one bounded metadata transaction, not a multi-Candidate money transaction. The existing job/member foreign keys may take their ordinary key-share checks; no new Candidate business, Work, Case or financial lock is introduced. Keep module→enrollment-clock→command→run SHARE NOWAIT ordering and the private owner's original validation.

Add only `jobs:[]` to the existing closed service receipt, each entry its original `{job_id,job_kind,job_status}`. Maximum20, unique IDs, native kind/status; existing scalar job fields must equal the final entry or all be NULL for an empty array. Update the strict runtime parser and background publisher in the same batch: every READY entry is published, never only the last scalar. Keep a single protected subtransaction over the page if retaining current all-or-error behavior; an exception rolls back every new member/job/count and must explicitly clear the PL/pgSQL array/scalars before the original progressed:false blocked receipt. Do not return an array of rolled-back IDs. Do not retain earlier committed entries yet falsely say no progress. The original error marker stays on that first command. A zero-job original advancement still returns the original progressed:true receipt and empty jobs.

For an uncontended30-Candidate original command this changes E from30 to2 native enrollment RPCs/queue turns. Generally E is ceil(N/20), with larger N requiring more pages and no Candidate/Timesheet cap. The illustration's total becomes962 rather than990 RPCs; at assumed100ms/two consumers its work term is48.1s rather than49.5s, still before Q/Create overhead and still NOT_MEASURED. The larger benefit is fewer queue handoffs, not removal of financial pages. No new input, RPC/action, command, storage or receipt identity is required; the bounded array is an additive result on the same service. Root approved this precise supporting boundary; source review of implementation remains separate.

Chosen PREPARE turn: at most16 original STEP pages per job, each preceded by its own fresh CLAIM. The normal PREPARE queue handler shares a10s soft RPC-start budget across that turn; other financial kinds remain one page. The accepted-SEAL task shares one10s start budget across at most two enrollment pages and at most two original PREPARE jobs concurrently, each capped16 STEP pages (at most32 total). The service clears the old lease after every validated nonterminal STEP; chaining another STEP with that nonce is invalid. Continue only original economic phases NEW/PINNING/RESERVE/ALLOCATE/FINANCE_ALLOCATE and WORKBENCH_WORK/WORKBENCH_CASE. WORKER_RELEASE_WORK/CASE/FINAL, expiry/discard retirement and all other financial kinds receive no extra drain. If a fresh CLAIM has already acquired a lease, complete its original bounded STEP or use existing failure recovery; if it reveals a release phase, execute its original one page then stop. Do not abandon that lease merely because the soft timer expired or the phase is excluded from extra pages. Start another CLAIM only after a validated continuing economic/projection outcome and before the10s start budget expires. Preserve the existing lease/owner/epoch/phase/cursor validation and PF08 failure recorder; no active foreign lease is adopted.

At most two distinct job calls may be in flight within one accepted-request task; that is a per-task bound, not a new global concurrency guarantee across HTTP requests and the two queue consumers. Publish every native READY identity before inline attempts, so the durable queue fallback may legitimately win CLAIM and stop the inline attempt safely. Stop extra work on no progress, blocked enrollment, durable deferred/attention, active lease, unknown reply, cancellation/expiry or the soft deadline. Await publication of every remaining native `{id,kind}` continuation before ACK or task completion. Never assume a previously published job stays yours. These limits bound added work, never economic size; larger Runs continue through original native pages.

Every in-flight RPC retains its existing8s error deadline. Allow for a CLAIM/STEP pair already started and for remaining publication when assessing the turn; the10s soft start timer is not a10s hard wall-clock proof. A bounded turn reduces queue handoffs but does not remove CLAIM/RPC latency or by itself prove all300 finish60s. With the public20-member metadata page, the normal ENROLL handler remains one service call per delivery. Accepted-request support starts from at most two pages' bounded native jobs, not an agency/Run array. Queue configuration and the other financial handlers remain unchanged.

Root chose this bounded support before genuine installed measurements; throughput acceptance remains NOT_RUN. No queue change can be inferred from the illustrative200ms assumption. Any later exact AUTH-QUEUE decision would require actual evidence that accepted-request drains cannot meet the card.

## Root scope and settled implementation

BD140 selects the narrow support required by the card's DB enrollment-page and bounded Worker-turn clauses. The checklist names the existing background consumer/minute tick (context D02) and this design (context D01); the card additionally requires native enrollment pages, preserved step identities and the PF02 checklist. Exact product objects are one full successor of public.bpay_next_enroll_service_v1(), the existing runtime enrollment receipt parser/publisher, the existing financial queue handler, and the accepted preparation wake seam in index.js. No private enroller, financial SQL/page/kernel, table, public trigger, Source/query producer, command, route or queue configuration changes.

The selected DB page contains at most20 jobs for one original PREPARE command: Run selection SEALED, Run PREPARING, command ENROLLING, genuine Run-command/accepted-command identity, and no OFFICE worker action. Its whole-page protected block retains the original rollback/blocked receipt; clear jobs/scalars on error. Other commands keep one original call. Every READY array entry is published before an optional inline attempt. The scalar last-job tuple and closed jobs array must agree exactly.

Worker economic PREPARE turns allow at most16 STEP calls with fresh CLAIM per page and a10-second soft start budget; each started CLAIM completes its bounded STEP or original failure recovery even if the budget expires. Stop extra looping for WORKER_RELEASE phases, terminal/retired/unknown/deferred receipts and worker_status CANCELLED (including release projection through WORKBENCH_WORK/CASE). Other kinds retain one STEP. An accepted SEAL alone may start ctx.waitUntil support: at most two enrollment pages, then at most two PREPARE jobs concurrently sharing that original10-second start budget. The original queue wake and every enrolled READY identity are durably published first; a competing claimant may therefore win and safely stop inline work. No active lease is adopted. This is finite latency support, never a claim that all300 finish in60 seconds.

The10-second start budget leaves room for an already-started pair of existing8-second RPC deadlines; it is not a hard completion promise, and native queue/recovery covers interruption. Cloudflare documents a shared30-second post-response waitUntil allowance, so accepted support must be optional and backed by durable wakes: [official context documentation](https://developers.cloudflare.com/workers/runtime-apis/context/#waituntil), checked12October2026. No runtime experiment was performed.
