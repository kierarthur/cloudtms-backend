# F-25 Candidate, Umbrella and finance-policy producer protocol

Read-only source design, 9 October 2026. No SQL/runtime/tests/fixtures/hosted calls or product changes. Scope is only Candidate `(pay_method,umbrella_id,min_take_home_wtd)`, Umbrella `(vat_chargeable,enabled)` and the original immutable NEXT finance-policy transition. Preserve 1590/1600 and existing agency_sequence; do not journal TSFIN/Contracts or create a second policy owner. This note supplements `F-25-nonqueued-producers.md` with actual trigger and finalisation seams.

## Recommended executable shape

Use **BEFORE STATEMENT entry**, **AFTER ROW actual OLD/NEW staging**, and **a deferred own-metadata finaliser or genuine outer-owner final tail**. The finaliser runs after all immediate row/statement callbacks, pre-closes exact FK/deferred business work, then receives one bounded metadata command using 1404. A deferred constraint trigger is a scheduling device, not a promise to execute last after every other deferred trigger.

The saved 2153 migration already defines `bpay_next_input_version_event`, typed Candidate/Umbrella/policy children and `bpay_next_input_version_receipt`. Reuse those exact authorities. Its event-to-final-receipt FK is DEFERRABLE INITIALLY DEFERRED; it is not a clock-taking finaliser and does not itself allocate order. The supplied `original_command_id` FK is deferred; standalone settings events leave it null rather than inventing a Source/WORK command.

Add a private transaction-local latch keyed by `pg_current_xact_id()` (xid8). Typed state: original module owner/epoch, owner mode `RAW_SETTINGS` or named outer owner, `OPEN/FINALISING/CLOCK_SEALED`, staged count and exact owned request identity where available. It is operational staging, not another accepted sequence. Service/browser roles cannot mutate the latch. GUCs alone are caller-resettable and cannot be the sole enforcement witness. A narrowly audited transaction-local helper may use a GUC only as an optimisation; the private latch is authoritative.

Suggested new helper/trigger contracts:

1. `private.bpay_next_settings_statement_enter_v1() returns trigger`: first action is a plain latch read; if CLOCK_SEALED, raise `BPAY_NEXT_PARTICIPATING_MUTATION_AFTER_CLOCK` **before** taking module or target-row locks. Otherwise lock module `FOR SHARE`, retain the observed owner/epoch, then create/reuse OPEN latch. Under non-NEXT preserve factual administration without NEXT version commands. For finance-window statements additionally lock `bpay_next_valuation_policy_control(id=1) FOR UPDATE` here, before window tuple locks; original 1324 callback can reacquire that same held row and retain its unchanged copy/advance semantics. Entry must tolerate INSERT … ON CONFLICT triggering both INSERT and UPDATE statement paths without making a second producer.
2. `private.bpay_next_candidate_input_stage_v1() returns trigger`, `...umbrella_input_stage_v1()`: require the OPEN owned latch, inspect real OLD/NEW only, and skip equal financial tuples. INSERT records genuine initial presence. UPDATE records actual before/after tuple, event xid8/epoch and digests using the existing typed child fields. No clock. Candidate pay-method/umbrella data must come from database OLD, not the Worker's incomplete before GET. Do not copy bank/contact fields. Append each material change; several same-row changes are distinct events and resolve in actual ordinal order, not random UUID order. Add an explicit stage ordinal if current schema lacks one.
3. `private.bpay_next_policy_input_stage_v1(old_policy_id uuid,old_policy_no bigint,new_policy_id uuid,new_policy_no bigint) returns uuid`: called by a complete successor of the original `bpay_next_finance_policy_change_v1()` after its **existing** window copy and pointer update. Stage old/new immutable policy IDs/numbers; do not rebuild/copy rates a second time. Preserve its four AFTER STATEMENT attachments, including DELETE/TRUNCATE and existing no-op-statement behavior. Do not receive the agency clock inside this callback.
4. `private.bpay_next_settings_finalize_v1() returns trigger` plus callable `private.bpay_next_settings_flush_v1() returns uuid`: one transaction-scoped batch of staged settings events, exact bounded receipt/hash, then one command kind such as `INPUT_VERSION`. Normal raw handlers affect one entity per REST transaction; reject an unsupported oversized participating batch rather than agency fanout. Before clock: hold all event/typed-child rows and referenced owner/policy targets already staged, validate epoch, finish applicable named deferred business checks, compute final digest and final receipt mapping. Set FINALISING; call existing `bpay_next_receive_command_v1(command_id,'INPUT_VERSION')`; append receipts referencing only the newly inserted command and already-held event rows; set CLOCK_SEALED. Subsequent deferred invocations verify exact receipts and return. No row/business locks, policy copy, snapshot refresh, outbox upsert or WORK query after this clock.

The final command contains exact event membership/digest and no financial job. Add a finite explicit `INPUT_VERSION` branch to the final `bpay_next_enroll_one_v1`: verify module epoch, original event/receipt set, mark the command complete and advance enrollment sequence once. Do not fan out to every Candidate of an Umbrella or materialise a policy-wide Candidate list. Umbrella and policy versions are looked up only for the selected accepted-input scope.

## Trigger attachments and terminal enforcement

Attach BEFORE STATEMENT triggers separately for INSERT and UPDATE OF the three Candidate financial columns; INSERT and UPDATE OF the two Umbrella columns; INSERT/UPDATE/DELETE/TRUNCATE on finance windows. For UPDATE, statement entry is intentionally based on the SQL SET column list, so even a same-value participating SET after clock refuses before acquiring its row. AFTER ROW still suppresses equal-tuple version events. Unrelated Google identity/contact updates do not enter a Candidate financial-column UPDATE trigger. Creation may have no existing row yet; stage its real generated ID, not a Worker guess.

Do not widen normal Candidate/Umbrella DELETE/TRUNCATE authority. Candidate delete has its own guarded owner; Umbrella delete may cause Candidate `umbrella_id` ON DELETE SET NULL. If either later becomes supported inside NEXT, it must enter the original outer delete owner before any row/FK action, with explicit deletion evidence. A child row UPDATE trigger is too late to establish that outer order. Until closure, refuse the affected operation/accepted input truthfully rather than silently dropping historical proof.

Modify the common 1404 receive-command body immediately **before** `SELECT ... bpay_next_command_clock ... FOR UPDATE`: initialise/validate the transaction latch and mark clock use before/with the first clock acquisition. Every existing accepted-command caller then protects these three settings against a later participating mutation. Only the owned FINALISING helper may receive its settings command while stage rows are pending. Other callers with pending settings receive `BPAY_NEXT_INPUT_VERSION_PENDING`; do not automatically flush from arbitrary nested publication code, whose later business locks may be unfinished. The existing SEAL_ENQUEUE owner may explicitly flush after all its required business/preclock work and then receive PREPARE, retaining one original cutoff. Replay clock access is also terminal for subsequent participating statements; never allow a replay to act as a lock-order bypass.

For raw settings POST/PATCH/DELETE, the commit-deferred own-metadata finaliser sees all immediate callbacks complete. An explicit `SET CONSTRAINTS <own finaliser> IMMEDIATE` can fire it early; CLOCK_SEALED then rejects later participating statements. Multiple settings statements before that seal are one bounded stage batch. Explicitly call the same flush at the real tail of owned multi-statement RPCs. Private latch state must survive until transaction end; do not delete it early and thereby permit another command. Transaction rollback removes both stage and latch; final versions/receipts remain append-only. An orphan stage must still fail the existing committed-receipt FK.

## FK and deferred closure: what is actually provable

For normal raw single-relation settings REST transactions, the finite immediate callback graph above has no demonstrated deferred business mutation other than the **legacy** scope-generation machinery. Module is preheld by statement entry. 0555 counter-stage callback returns for non-LEGACY; generic `candidates`/`umbrellas` counters do not meet the `pay_candidate:<uuid>` scope pattern either. Original fresh NEXT dirty paths therefore do not justify invoking legacy `pay_workbench_scope_change_finalize_trg_v1()` at commit. If an owned mixed transaction does create that real deferred callback, it can lock counters/jobs and global generation; explicitly complete its original named constraint before the settings clock or reject the unsupported mixed owner. Do not `SET CONSTRAINTS ALL IMMEDIATE` or assume an arbitrary deferred callback is harmless.

Actual owner FKs: baseline finishing :7100 Candidate job_title → default_job_titles, :7103 Candidate umbrella → Umbrella ON DELETE SET NULL; neither is declared deferrable. Candidate PATCH may include job_title alongside financial fields; finish normal statement RI checking before metadata finalisation. Umbrella has no outgoing business FK in the examined base definition. Policy control/window reference original immutable policy rows; original copy/advance and typed policy stage run before clock. Window overlap exclusion `settings_finance_windows_no_overlap_excl` :4620 is not declared deferrable; retain it unchanged.

Existing 2153 children reference Candidate/Umbrella/policy and their own event rows immediately. Stage them before clock while the owner rows/immutable policy IDs are already held; these are the exact preclock FK checks. Event original-command deferred FK is null for standalone settings. Receipt FK points to the command just inserted by this transaction and the event rows already held. The deferred reverse event→receipt FK points only to the newly inserted own metadata receipt, so it introduces no new foreign business-row acquisition after clock. Force that **own named receipt constraint** after receipts exist if desired; it cannot replace original business-FK closure.

A generic deferred trigger cannot certify the end of every arbitrary mixed service transaction: another deferred callback can execute later and acquire business rows. The supported normal raw handlers are finite single-REST writers; their graph is closeable. The dedicated pay-method RPC needs the explicit outer successor above. For arbitrary multi-statement mixed owners, require a named outer final-tail protocol and guard participating writes after the clock, or refuse the unsupported combination. That is a truthful bounded gap, not a reason to invent a global journal or second order.
