## Decision and bounded protocol

F-25 card 01:1039–1055 and checklist D01/D02/D05–D08 require only genuinely unbound inputs to join the existing `bpay_next_command.agency_sequence`. R2 §4 requires exact immutable query evidence and participating nonqueued query mutations in that same order. The existing query facts reader already has the substantive qualification logic and immutable evidence references. Preserve it; the missing pieces are historical mutable-tuple versions, outer admission, and a genuinely final producer tail.

Use two phases. A narrow row hook stages actual OLD/NEW query tuples and original evidence IDs without taking the agency clock. The genuine outer owner finishes its business locks, all gate-relevant writes, callbacks and implicit foreign-key work, then seals staged versions against its existing publication command(s). Standalone query actions which do not already publish an ordered command receive one bounded metadata command at their final owner tail. **Never issue a second query command for already ordered Source publication.** A Source pair already produces its existing per-WORK commands; retain those command IDs/sequences and their exact root/event association, rather than collapse them into a new invented pair order.

Suggested private helper contracts (new names, not claims of installation):

* `bpay_next_query_producer_enter_v1(owner_kind text, request_key text, request_sha256 bytea) returns uuid`: fresh outer owner, after pure validation/exact immutable replay, before its first transaction/business/module lock. Calls existing `weekly_source_pay_query_admit_v2()`, then acquires the stable module decision and creates a transaction-local producer token. No agency clock. An exact reply replay creates no token/version/command.
* `bpay_next_query_version_stage_v1() returns trigger`: only actual relevant tuple changes, insert or delete; record source kind/ID, ordinal, actual before/after facts, exact scope keys and immutable evidence IDs. No clock, module row lock, WORK lock or foreign key to mutable business tables in this staging operation. Reject a participating fresh mutation after this producer's final seal. Preserve several same-transaction mutations in ordinal order; do not erase a meaningful intermediate event by silently coalescing it.
* `bpay_next_query_producer_finish_v1(producer_id uuid, publication_commands jsonb) returns void`: strictly validated mapping of actual command IDs, WORK/root/event IDs and module epoch. For existing publication verify original immutable publication/revision receipts and command sequence; never allocate another sequence. For standalone query actions derive/reuse the genuine original mutation key, persist a metadata receipt and receive exactly one metadata command after business work. Metadata enrollment must be an explicit finite no-financial-job branch in the final `bpay_next_enroll_one_v1` successor; otherwise a new kind can strand the clock.

Version authority needs typed `producer_id`, transaction identity, staged ordinal, object kind/ID, Candidate/client/Contract/work date or family scope, actual OLD/NEW state tuple, original event/comparison/review/publication IDs, request hash, cause kind/key, module epoch, original command ID and agency sequence, and immutable before/after digest. Append-only final versions plus a transaction-local pending token are sufficient. No fabricated prehistory/agency sweep. Exact absent-object/initial-state evidence must be captured for the selected scope; missing historical coverage is a typed refusal, not today's state substituted for an earlier cutoff. FK checks on immutable version evidence must be completed/prelocked before clock acquisition too.

At accepted Enqueue enter the existing query admission lock before its first module/business lock; capture the original full gate facts and selected-root scope with accepted_input/effective_work_cut. After earlier commands drain, the resolver may incorporate their exact immutable earlier versions/qualification receipts, bounded by accepted sequence. It must exclude later tuple versions and later Source pointers. A hash or an OPEN/RESOLVED flag alone cannot reproduce the gate. Existing `run_work_query_pin_v2` remains the per-WORK captured CLEAR witness. Missing/damaged/unavailable evidence refuses before capture; do not manufacture CLEAR or apply a fresh later query check to an accepted pin.

## Honest remaining closure limits

No fundamental requirement gap was proved unresolvable. There are real implementation gaps: uncovered outer Candidate entry, ordered receipt publication with later binding/push/FK work, and a scope finaliser that can lock at commit. Source-only inspection cannot honestly certify absence of every transitive FK/notification lock or arbitrary service-role multi-statement caller. The final root change must either close those finite actual paths and enforce token/terminal ownership for raw participating writes, or refuse accepted inputs whose relevant version chain is incomplete. An undocumented assumption that “commit happens next” or trigger alphabetical order is not a lifetime proof. Current source does not justify ticking a completed producer protocol merely because the facts reader has immutable references.
