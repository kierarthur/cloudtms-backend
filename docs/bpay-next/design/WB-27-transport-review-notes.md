## Exact pitfalls and source findings

1. **Keep the final recheck even when there are zero Case rows.** Ordinary completed pages have no next cursor. The saved estimate branch additionally returns a verification cursor, including a null native key only for the exact zero-row case. The final call must carry the complete descriptor/version scope and `verify_only:true`. SQL rederives the whole bounded plan/current version set before checking the terminal cursor; it refuses a nonterminal verify request. Empty suffix alone is never freshness proof. Worker/FE response validation allows zero rows only on a completed estimate and requires the bound verification cursor (Worker 475–480; SQL 566–601).

2. **Validate the complete continuation request, not only the versions array.** The wire repeats descriptor/version facts inside `after.context.estimate_scope` and the ordinary estimate object. All encoded query bytes, wrapper keys, descriptor/context, cursor and final request must fit 32768 bytes before first-page continuation is offered. Worker independently bounds its service RPC body too. The current SQL uses a conservative three-times complete JSON bound, while Worker/FE construct an encoded continuation for a second check. Their size helper currently labels the path `/api/bpay-next/workbench?`, while the real Office route is `/api/banking/pay/next/workbench-page?`; keep the envelope measured consistently against the actual guard. The conservative SQL bound avoids silently truncated scope. Oversize must yield honest PENDING. SQL's 120000-byte response budget remains narrower than the existing 131072-byte transport cap (SQL 598–614; Worker 469/638/653/660; FE 470/656–657).

3. **Native versions are comparison operands only.** The saved version validator accepts bounded three/four-string tuples and deduplicates whole tuples. Therefore SQL's complete sorted current-set equality is indispensable: it must reject unknown, missing, repeated-identity/conflicting-version and added/removed operands as OUTDATED. Neither Worker nor FE may dynamically dispatch on tuple labels, read money from them, or treat their syntactic presence as currentness. Literal consumed relation/identity sets remain the separate native-input review's responsibility. No digest, token, signing secret or browser proof is needed (Worker 465–467; SQL 275–352).

4. **Response money/reasons need their native semantics.** The current estimate schema uses generic `decimal` and `code`, which also admit sub-penny/negative recoverable strings or unknown cap labels. For strict estimate response validation, recoverable amounts must be finite nonnegative pennies; totals must retain each field's legitimate native sign. Cap reasons come only from existing 0290: TAKE_HOME_FLOOR, EARNINGS_THRESHOLD, PAY_HEADROOM, CASE_CAPACITY, or null; affordability/capacity subsets remain exact. Validate syntax/meaning without computing allocation in JavaScript (Worker 12/441/477; FE 14/443/478; original `04102026_0290_banking_pay_next_case_allocation_row_v1.sql`). This is boundary hardening, not a demonstrated wrong SQL result.

5. **Reject duplicate component identities across the whole bounded walk.** Strict tuple ordering alone does not reject the same component with a different age/case/ordinal. The latest FE source already closes this pitfall with its bounded Map, rejecting duplicate `case_component_id` before adoption, while keeping rows/bytes within the original technical budget. It also compares complete context and all totals across pages and after the final fresh read. No partial page is adopted (FE 1408–1424).

6. **Open UI issue: keep old changed-tick money stale during UPDATING.** At this review, starting Show estimate sets UPDATING but retains the previous `estimateResult` and `estimateRows` (FE 1406). Row/detail stale styling applies only to OUTDATED (1471/1300). After ticks made a prior estimate Outdated, starting another request temporarily displays those old figures without their stale styling. Clear prior result/rows at request start, or retain their stale styling through UPDATING until final adoption. Root was notified. The button alone invokes the reader; selection callbacks mark Outdated locally and do not request an estimate.

7. **Preserve the existing window/selection fences.** The latest FE walk captures one immutable descriptor/local revision/memory reference and ordinary context, checks current owner/actor/window plus its estimate ticket after every await, compares complete page scope/totals, and adopts only after the final same-reader check (1401–1426). Closing invalidates the ticket and drops estimate rows (1505). Keep these checks when changing layout, detail callbacks or refresh. A new tick must not allow an older successful response to overwrite the changed selection. Disclosed before/after counters within one SQL statement are not a concurrency proof.
