## Three essential design conditions

1. **Preserve old pending bytes.** Office `requestBody` at 397–405 is reused by transport at 504 and journal hydration at 956 to reconstruct exact pending bytes. Making a token mandatory in that sole decoder would reject genuine old tokenless journals as JOURNAL_INVALID. Keep the exact historical closed tokenless form readable; new first protected dispatch separately requires the new helper/token. A previously unknown request gets only the same action/UUID/operands/token bytes, including a retained expired token for original receipt qualification. Never attach a fresh token, re-preview/re-scope, generate a UUID, clear a pending journal or start a conflicting action merely because a later authentication/refusal response occurs. The original `dispatch(previousOutcomeUnknown)` rule at 981–992 already preserves this boundary. Root accepted this requirement.

2. **Re-download is original receipt retrieval.** Current STATUS row schema at Office187 has no instruction UUID. Office1606 otherwise generates `controller.newId()` when the retained original transfer/instruction pair is absent, even for ISSUED_CSV. Native CSV owner evidence in investigation section CSV_ISSUE (:76; original0316:195–212) proves a different instruction UUID on an issued transfer refuses. The exemption therefore applies only to the exact existing instruction/transfer and native original issuer/receipt checks. Root's chosen smallest closure is an inline refusal when the original identity is unavailable, with no guessed/reissued UUID and no extra reader/framework. A cold retrieval capability can only be supplied by its genuine later native authority, not by this design inventing a value.

3. **Password-only button must name the action.** SCR-66's Send code is the genuine code-required password step; SCR-66b's final button names the actual action. Under a legitimate configured no-code policy, a button labelled Send code must not directly dispatch cancellation/file issue. Root will expose authoritative preview policy metadata for display and show the actual action for password-only; START still decides current policy. Policy changes or uncertainty refuse rather than infer password-only from the browser. The reason/password-only scheduled-cancellation exception applies only when its exact later CANCEL_SELECTION/SCHEDULED owner exists; no current CANCEL_REQUEST or TEST shortcut.

The complete serialized protected command, including signed token metadata, must fit the existing 2,048-byte UTF-8 envelope. Validate its closed shape/byte budget before saving/first dispatch; do not enlarge it or truncate. Keep the existing Worker 8,000ms command deadline and 128KiB result budget; an aborted/lost reply is unknown and preserves bytes. Credentials/code are never stored in the journal. Only the finite original command token is retained for its exact replay. The receipt schema/cross-checks stay unchanged and do not expect a raw token echo.

## Smallest complete Office flow / layout

Implement the named NEXT password/code helper in `js/bpay-next-office.js`, plus a progress-context variant which delegates to it. Export those concrete helpers for the present and later owning callers; a string/enum entry alone does not satisfy D08/D13. Reuse the existing standard small-window adapter and finite transport. This needs no new module, batch list, execution parent or live-money calculator.

The caller captures its native action/UUID/complete typed intent and current actor/agency/NEXT context, reads the bounded server preview, validates its exact action/identity/context and displays its authoritative Candidate facts/count, total and truthful monetary basis. CANCEL_REQUEST before accepted cash shows frozen gross being removed, not a guessed bank amount. A later native state/policy change is rechecked on server first acceptance. The intro never implies a payment date or sent money.

Open the small “Confirm it is you” native dark child with one action subject block, one active credential field and one primary footer step. Password input uses the native password control; code step replaces it with Email code, inline plain wrong-code error and Send a new code secondary. The final button names the actual action. Close remains in the header; focus moves to the active input and wrong code remains at the field with alert, progress/result is status. Use actual native reason only for a caller whose typed action has one. Freeze/requalify that reason and every operand; editing it invalidates the old preview/challenge rather than silently authorizing a changed intent.

While the child or a request is busy, suppress conflicting parent mutation/selection. Validate actor, owner, exact parent frame, typed identity/operands and live child ownership after preview/START/VERIFY and before journal dispatch; an old late response cannot write into a different parent. Closing/dismissal resolves once, discards credentials and resumes the original native parent, without changing its journal. Successful proof closes this exact clean child and only the still-qualified caller saves/dispatches its complete original request. Unknown financial reply exposes the original exact retry; no fresh proof dialogue is opened for that retry. Already accepted service pages/jobs continue without reauthentication.

In-progress-window reuse is a concrete helper variant preserving the exact current progress parent/command/cursors and same controller. It is callable now without inventing a RELEASE_REFUSED UI before its later card. Current CANCEL_REQUEST and first CSV_ISSUE are the two existing Office entrypoints to wire; PAYE_NET, TRANSFER_BEGIN and preparation Remove/Discard do not become protected merely because they are nearby.
