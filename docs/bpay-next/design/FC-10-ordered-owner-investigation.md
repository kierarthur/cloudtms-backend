## 1. Native kinds and progression

There is no native command-kind or job-kind enum/CHECK to broaden. `03102026_1324_banking_pay_next_core.sql:795–808` defines `command_kind text not null`; its existing command status CHECK is `RECEIVED/ENROLLING/SEALED/COMPLETE/FAILED`. `:967–991` defines `job_kind text not null`, `READY/LEASED/BLOCKED/DONE/FAILED`, unique `(command_id,candidate_id,job_kind)`, exact command-sequence/member FKs and the equivalence between LEASED and nonnull lease nonce/deadline. Preserve those checks. `03102026_1404_banking_pay_next_command_intake_v1.sql:27–58` admits a nonnull kind of 1–64 characters, assigns one agency sequence under the original clock, and refuses reuse across kind or module epoch. CASE_PAUSE and CASE_RESUME fit the existing native contract; a third generic control kind is unnecessary.

Use two explicit action/kind identities and one Candidate member. Fresh admission follows the current FC09 pattern: native Case derives Candidate; module/admin qualification; Candidate/control lock; original command UUID replay comparison; Case/component checks; `receive_command`; member 1; immutable request; command SEALED with expected count 1. Current reference is `11102026_1939_banking_pay_next_case_edit_v1.sql:171–229`; intake's service-only/admin/NEXT boundary is `:409–450`. Closed FC10 input is exactly command_id, case_id, expected_case_revision and required-nullable reason, plus the transport action; no browser Candidate or target status operand is needed. Both action and null-normalized reason participate in original replay equality. BD120 chooses 2048 UTF8 reason bytes/no NUL and a scoped 16384-byte request ceiling; preserve the current limits for every other action.

`enroll_one_v1`, current1939 `:753–764,957–973`, locks the original module/enrollment clock, handles only sequence last+1 and inserts one READY/NEW job before advancing enrollment. Add the two finite branches with request.action equal to command_kind, request module/sequence/member/Case/Candidate equality and SEALED/count checks. Existing member/job uniqueness prevents double enrollment. Do not substitute a zero-job snooze receipt branch: pause/resume must remain ordered relative to Candidate preparation.

## 2. Necessary immutable request and outcome

BD120's two private tables are sufficient. Request primary identity is original command UUID, with native `(command_id,candidate_id)` member FK and `(case_id,candidate_id)` Case FK; actor FK; action; module epoch/accepted sequence; expected revision; captured prior and target OPEN/PAUSED statuses; optional normalized reason; accepted timestamp. Action/status checks make PAUSE OPEN→PAUSED and RESUME PAUSED→OPEN. Native sequence/time come from the original receipt, not the browser. No CASE_CREATE FK is appropriate: genuine automatic Overpayment recovery has no manual creation request. No Rule or period storage is needed.

Outcome is append-only, unique to that exact request/member/Case/Candidate and exact original native job. It records APPLIED versus BLOCKED, terminal time, closed issue code, applied status/revision or null, and captured protection summary/first address or null. The job's command/candidate/kind must equal request identity, not just an existing arbitrary job UUID. APPLIED requires null issue, target status and expected+1 revision; BLOCKED requires a known issue and **null applied status/revision**. Do not copy FC09's `expected+1/new_rule_id` result shape on BLOCKED (`1939:305–307,364–365`): those are FC09 amendment fields, not evidence that this toggle happened.

An immutable terminal outcome is essential because mutable current Case status can change again, and current job.last_error_code alone does not retain the blocked protection facts. No money event is required or appropriate. Native event kinds remain the existing APPROVED/FUNDED/RECOVERED/PAID/SHORTFALL/WRITTEN_OFF/CORRECTED (`04102026_0300_banking_pay_next_case_instruction_core.sql:494–495`); adding PAUSED/RESUMED or a CORRECTED event would expand money history and interfere with the FC09 preactivity event predicate. Original Case/principal/Rule/age/period/hold/result rows stay intact.

Reuse original private ownership, revoked browser/service table ACLs and immutable guard pattern (`1939` migration `:69–71`; repeatable `:3199–3204`; original `1342:188–198`). A narrow insert guard/constraint must close the typed tuple and outcome alternatives; update/delete/truncate refusal belongs on these new append-only tables. Do not edit the shared immutable guard or introduce public triggers. Only required request/outcome point/FK indexes are support; no agency history projection is needed.

## 5. Known lifecycle faults versus retry

Use a status mutation subtransaction like `1939:313–361`, but with a **finite FC10 issue list**: expected revision changed, unsupported recovery membership/terminal Case, same-target refusal, FC16 pending/protected/balance-invalid. If translating native FC16 codes to one public held-by-Draft code, retain exact typed summary and first address. Capture diagnostic detail/state for the original failure; append the terminal outcome after the status subtransaction rolls back. APPLIED outcome and terminal job/command completion must commit atomically with status/revision/refresh. BLOCKED outcome and job DONE/DONE plus command FAILED commit atomically without an applied status. Any failure while writing the outcome aborts the whole step.

Never catch all check violations or all 55000 as BLOCKED. Missing request/outcome identity, malformed native tuples, invalid lease/epoch, missing dependency, unexpected SQL error and response overflow rethrow. In particular, 55P03 is outside the known-fault handler. Current `broker/src/bpay-next-job-step.js:386–387` maps 55P03/serialization/deadlock/timeout to retryable transaction retry; `bpay-next-financial-queue.js:67–82` retries before its permanent-failure callback. No extra Worker fault mapping or terminal-review state is necessary for this fence. An uncertain STEP retry wakes original `{id,kind}`; current queue `:143–176` takes a fresh CLAIM, never a copied active token, and ACKs only a definitive terminal result. Native lease expiry governs recovery.

Protection can appear between admission and ordered application. BD120 intentionally re-proves it: that original request becomes BLOCKED with retained facts, never a later reprice or frozen-state rewrite. The current plan deliberately consumes accepted memory Case status/rule (`1939:1786–1815`) and skips non-OPEN nominal collection (`:1958–1959`). Do not change this accepted-cut behavior to rescue a later blocked status request.

## 6. Closed native protection and CASE_COMPONENTS extension

Existing binding shape is exact and sufficient (`1509:12–14,149–164`): binding_kind HOLD/PENDING; run_id; case_component_id; native_id; candidate_id; nullable run_worker_id; channel; run_status; nullable worker_status; actor_user_id; nullable preparation_revision; nullable protected_amount; next_action. Next actions are CANCEL_CANDIDATE_PAYMENT, REMOVE_CANDIDATE_OR_DISCARD or DISCARD_PREPARATION. The existing reader adds actor_display_name only (`:208–219`). No pay date, PB number or derived date is needed.

Whole-Case summary remains the guard's exact four fields (`1509:259–292`): unreserved_capacity nullable numeric text, protected_count bigint text, protected_amount nullable numeric text and next_cursor. Any continued protection list must reuse the existing bounded cursor, not a browser inventory.

Existing public request keys `1939:2746–2751` and exact readback `:2791–2802` show the minimal extension: optional exact pause_command_id UUID (alongside preserved edit_command_id compatibility), qualified by requested Case and Candidate; attach the immutable receipt on those original rows.
