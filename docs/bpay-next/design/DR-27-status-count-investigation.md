## Exact count, generation and traversal — design choices to settle before product

1. **One list predicate.** Exact current agency, confirmed/list-visible row, allowed operational filter and sort; includes confirmed COMPLETE/CANCELLED. List/count must use that identical predicate and context. Normal default keyset is(created_at_utc DESC,run_id ASC,pay_channel ASC); equal timestamps and both channels require all three terms. A filter change is a new scope, not continued old pages.
2. **Per-row revision is insufficient.** The last row's totals_revision/change_revision does not notice a newly confirmed row ahead of it or another row moving into/out of the filter. max(transaction sequence/nextval/change_revision) alone is unsafe: an earlier allocated value can commit after the larger visible value, leaving that maximum unchanged. Sum/max over all financial histories is not a maintained generation.
3. **Small list metadata support if immediate counts are required.** A single agency-scoped display metadata row containing list generation and finite status counts is narrow supporting authority; it contains no money or duplicate Run/channel totals. The one typed apply owner changes old/new visibility/status counts and its generation transactionally. All-status count is the same finite stored status-count sum. Row movement subtracts old filter membership/adds new exactly once. This solves exact count without an unbounded financial/history scan. Do not silently put this counter on module_control and upgrade existing module SHARE locks after Run/Worker locks: two readers upgrading the same module row can deadlock. The exact physical metadata choice and lock position must be recorded in the build design; no framework/cache/queue is required.
4. **Global display lock must be a proved leaf.** Native order is module→Run→Candidate→job→Worker→channel summary. If the global list metadata row is locked, acquire it only after the final native business lock/mutation of that transaction and never subsequently take another Run/Candidate/job/Worker or different summary lock. A generic Worker trigger that acquires the global row before a later multi-Worker/native loop can create a cross-Run cycle. Either the actual original owner already meets the leaf rule, or its exact final typed apply seam must be used; do not broadly reorder money owners. This is the critical concurrency requirement before choosing automatic hooks.
5. **Bounded count alternative.** A pure indexed summary-page count continuation with fixed per-call work can eventually return an exact final count under one context, never silently cap the result. It is not an immediate exact count until complete. If chosen instead of maintained metadata, root must explicitly solve generation and page-number addressability too; a cursor loop in the browser that loads every prior page does not satisfy the card.
6. **Page number is not a keyset cursor.** Native server keyset supports continuation. If DR28 exposes direct arbitrary numbered jumps, their server strategy must not require browser predecessor loading. An indexed summary OFFSET seek avoids that browser behavior but work increases with page number; do not claim it constant-bound. DR27's bounded keyset-only contract need not invent a rank/cache framework where no numbered jump is exposed. No hidden ceiling, all-row JSON or loaded-page sort. Source approval must check actual continuation/scope correctness, not merely that limit<=100.
7. **Read-only historical authority.** Service JWT/current active admin/NEXT/current agency check followed by STABLE native reads. Do not invoke preparation workflow-readiness authority that rejects paid/cancelled history. No Run/Worker locks, wake, ENROLL or financial operation on list/count. Closed typed args/filter/context/cursor/row/request/response limits; decimal strings for bigint and monetary facts. Read generation before/after relevant snapshot and refuse mismatched continued scope. No claim that a same-statement stable snapshot makes separate HTTP requests atomic.
