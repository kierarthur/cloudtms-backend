## Transaction protocol and lock proof

A plain AFTER ROW trigger that calls 1404 immediately is unsafe where the caller later locks WORK, revision, case, policy, family or publication rows. A deferred constraint AFTER ROW trigger delays its callback until transaction end, but **deferral alone does not prove the lock order**. The callback can still take module locks, implicit FK key-share locks, or run before another deferred callback which takes business locks.

Use the existing order: **Source global admission (where applicable) → module admission → original business/FK evidence locks → agency clock as final tail**. No later business lock after first clock acquisition.

1. At producer entry, retain exact replay behavior before new admission. Fresh query owners call `private.weekly_source_pay_query_admit_v2()` before business locks. Its existing try-advisory key is `CLOUDTMS:BPAY_NEXT:SOURCE_PAY_QUERY_ADMISSION:V2`; do not introduce a second cutoff key or sequence.
2. Acquire the module row SHARE before the producer's first competing business lock. For raw Candidate/Umbrella service INSERT/UPDATE, a narrow **BEFORE STATEMENT** guard can acquire it before target tuple mutation. A BEFORE ROW trigger is useful for UUID/typed staging, but UPDATE can already own its target tuple when it fires; that row trigger alone does not prove module-before-row. For multi-step RPC/Source owners which already lock earlier business rows, use the existing entry/admission seam, not a late table trigger presented as early admission.
3. A BEFORE/AFTER ROW stage hook captures the actual OLD/NEW tuple and stable event UUID; equal economic tuples emit nothing. INSERT keeps `old_present=false`. Avoid broad DELETE/TRUNCATE permission changes: reject unsupported deletion of a participating input or wire its genuine existing owner explicitly. Do not create a clock-taking BEFORE trigger.
4. Pre-acquire exact FK/evidence target locks needed by the eventual receipt INSERT during the business portion. RI/FK checks can take tuple locks even without explicit `FOR UPDATE`; they count in the proof. Gather/validate all bounded staged events and complete query owner state before acquiring the first clock. Existing immutable evidence rows can be referenced without a second mutable financial owner, but their FK lock order still requires audit.
5. A DEFERRABLE INITIALLY DEFERRED constraint AFTER ROW callback processes each exact queued event once, after all original writes. Before the first clock it validates the finite current-transaction pending closure and owner-final facts. The tail appends event-command receipts under 1404, with no new Candidate/Umbrella/WORK/case/query lock, no recursive receipt staging, and no producer continuation after clock. An already-receipted UUID must return its exact receipt after immutable identity/digest verification.
6. Retain every individual OLD/NEW event, including repeated same-row updates. Query gate evaluation uses the **completed transaction's coherent comparison/WAIT/publication state**, not the interval between incident INSERT and comparison-pointer assignment. Individual event identities are not collapsed; a shared final owner-completion/query witness may be referenced by each event. Deferred event order/actual clock allocation establishes their agency order; do not infer it from random UUID or wall-clock time.
7. Any other deferred constraints/triggers which may acquire new business locks must be prelocked or included in the same bounded final-tail proof. A naked generic end-of-transaction gate reader or late `SELECT module FOR SHARE` is not adequate proof. Normal module SHARE holders are compatible, but the DISABLED transition's conflicting module UPDATE and any worker/business recensus require their specific lock census; do not assume compatibility removes the stop-transition cycle.

The current 1540 Source pair publisher is the useful concrete model: it locks module, Candidate/worker control, all sorted WORK roots, old/new revisions and physical root witnesses **before** per-root 1404 command allocation. Preserve its all-or-none publication, replay and immutable receipt behavior.

## Mixed transactions, baseline and earlier accepted commands

At fresh SEAL_ENQUEUE, refuse if the current transaction has any relevant staged/unflushed nonqueued input event. Conservatively refuse all current-transaction F-25 staged events until narrower scope is proven. Return a typed conflict before PREPARE allocation; never clear/flush them with SET CONSTRAINTS then continue taking business locks. Also refuse unsupported financial-input mutation after this transaction has allocated PREPARE/clock unless the entire exact closure was already prelocked and certified. Raw HTTP changes commit first; their metadata receipts are visible before the next independent Enqueue.

Existing unversioned settings are not historical NEXT commands. At the first selected acceptance, under exact Candidate/Umbrella/policy/query scope protection, append a **`BASELINE_AT_ACCEPTANCE`** witness with actual values, exact PREPARE identity/sequence and digest. Do not seed every agency row, manufacture a “before-click command”, assign an observed timestamp as order, or claim historical reconstruction. Later OLD/NEW events preserve that baseline's applicable previous value. A witnessed earlier committed mutation uses its genuine last applicable agency receipt below PREPARE; a later mutation cannot replace retained accepted evidence.

Earlier queued changes remain their genuine financial commands. A known earlier WORK publication is retained at acceptance and resolved after its Candidate job completes. An unknown or unresolved earlier CASE_CREATE/funding/rule command cannot be treated as an empty current case set: **truthfully refuse before acceptance until it has resolved sufficiently to determine the economic choice**. F-25 permits that refusal. Later case creation remains excluded. Do not invent a finance data snapshot or generic rule command to avoid the original barrier.

PREPARE command members must exist at Enqueue for accepted-input FK integrity. Their exact selected identity/member_no is appended once; existing 1430 enrollment validates/reuses it and still creates one job per step with original counters. Materializing members is not early job enrollment or skipping earlier agency commands. All accepted-input/query-child FK target locks belong to the pre-clock closure.

## Zero-member metadata enrollment

Suggested closed kind **`INPUT_VERSION`** (actual receiver is `receive_command(uuid,text)`): one UUID event maps to one immutable command receipt. Existing already-ordered Source/finance publication completion references its original command rather than receiving a second command for the same financial action. Nonqueued gate/admin changes need the new metadata command only where no genuine accepted NEXT command exists.

The receipt tail supplies `expected_member_count=0`, `enrolled_member_count=0`, `status='SEALED'`, non-null `sealed_at_utc` only after exact immutable event/query evidence exists. The new 1430 branch, ahead of generic POSITION_APPLY fallback, verifies command kind, original epoch (or later explicit F-26 mapping), exact receipt UUID/digest/sequence and zero counts; verifies no command_member/job rows; advances `bpay_next_enrollment_clock.last_enrolled_sequence` only from `n-1` to this command's `n`; returns NULL. SEALED is already an allowed terminal enrollment state; do not invent a status or early COMPLETE behavior without a real command consumer. It cannot advance the enrollment clock in the producer or skip unfinished earlier commands.

Current `bpay_next_command` (1324:795) allows statuses RECEIVED/ENROLLING/SEALED/COMPLETE/FAILED, nonnegative counts, `enrolled<=expected`, and requires sealed timestamp for SEALED/COMPLETE. Enrollment clock is the existing singleton (1324:961). Current final 1430 falls through to `BPAY_NEXT_ENROLLMENT_COMMAND_INVALID` unless kind POSITION_APPLY after its existing named branches; receiving INPUT_VERSION without this branch strands the queue. 0560 already reports NULL-job metadata progress correctly, as noted above.
