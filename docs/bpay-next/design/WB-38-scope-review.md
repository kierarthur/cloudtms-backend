## Necessary support and review conditions

1. **A named context successor is necessary for the required opening defaults.** The current context requires `indefinite` to equal whether the requested date is null even for PRE_OPEN (`1100 repeatable:48–58`). It therefore rejects a new blank-date, indefinite-unticked window. Its returned date/note are the submitted input, not the active control's saved values (`130–156`). Permit the blank new-date shape only in PRE_OPEN and return the saved active date/note for amend. Preserve strict PRE_SAVE/SET date shape, London-today validation, worker-pay basis, expected version, exact Case revision and warnings. PRE_OPEN remains a pure read; it must not create an acknowledgement. Do not allow the opening exception to become a blank-date SET which silently means indefinite.

2. **Expose through current W1/W2 with exact readback.** The current 2150 W2 accepts RETRY_WORK_JOB only (`132–154`). Add only the card-required snooze actions, retain that complete retry branch, and inject the authenticated administrator through the existing Worker. `readback=true` must return an actor/action/body-matching original receipt or explicit absence without accepting a command or minting a warning token. The single private action replays existing receipts, but executes a mutation when a receipt is absent (`1100:187–224`); invoking that action for readback is unsafe. CHECK belongs to the current 0207 reader. Explicit ACK_ISSUE belongs to W2, and its exact token/context must be revalidated and consumed under the native lock by SET (`267–286`). A malformed/unknown response retains the original journal bytes and pauses conflicting controls; success readback clears only that request. No typing-time call or polling is needed.

3. **Freeze native expense and mileage membership once, with complete disclosure.** The current schema/context already admits approved EXPENSE and MILEAGE through EXPENSE_LINE (`1100:101–114`); no separate mileage financial scope or hard-coded list of three/four components is necessary. The MANY operation must name the exact Candidate, Work, immutable approved revision, physical Timesheet, approved line/component and worker-pay basis, together with the relevant control versions. Confirm the complete scope once before mutation; each mutation/result page is at most 100 lines, and a finite request/response byte bound must refuse honestly rather than truncate membership. Browser page arrays, name/date/amount guesses and claim-authorisation writes are unnecessary. Resume by the retained native request/page identity, not by re-enumerating a newer current revision.

4. **Deduplicated aggregate versus line controls are an essential explicit choice.** Current uniqueness prevents only duplicate active controls of the same scope identity (`1100 migration:45–46`). The original at-cut reader admits both EXPENSES_ALL and EXPENSE_LINE and selects their effective control (`1100 repeatable:465–474`). Hence creating per-line controls under an existing aggregate, or clearing per-line controls while retaining that aggregate, can misrepresent the user's result. The MANY design must define exclusive/deduplicated coverage and account for the exact existing EXPENSES_ALL control once. Never clear WHOLE_TIMESHEET as collateral to all-expenses clear: that would also wake wages. A retained whole control must instead remain visible as the native reason the expenses are still deferred. Do not weaken the original single active-control version checks to make overlap look successful.

5. **Failed-only retry needs an immutable operation and truthful results.** Successes remain recorded and are never executed again. Unknown pages first read back their identical bytes; they are not classified as failures suitable for a new request. A retry addresses only the failed native member set, retaining its once-confirmed identity/basis/control operands. A genuinely changed basis/version is stale/refused, not silently replaced with fresh operands. Changing the operation or re-freezing a new revision requires a deliberate new confirmed operation. Persisted per-line/page receipts must conserve actor, native sequence and exact event result; the original single receipt is append-only and proves exactly one event (`0255 guards:190–205/235–261`), so it cannot simply be relabelled as a multi-event receipt. Extend only the private frozen scope/result support this card actually requires, with no general bulk framework or financial command-member reinterpretation.

Preserve WB-37's strict DUE/null-system-actor receipt, manual receipt branches and qualified zero-job advancement. Keep original single snooze basis/action semantics and immutable at-cut history; R2's charge-only compatibility and exact segment-only scope remain intact. No whole-day sibling restriction, pricing, holds, reservations, settlement, Source, Pay Query, producer or row-kernel change is required. MANY accepted command completion must have a defined narrow advancement seam; it must not create an unsupported job or strand the original ordered command clock.

The current Timesheet handlers still call the old route (`main.js:363657/363717`); gate and resolve the native NEXT identity through the established owner rather than mapping a physical Timesheet UUID to a guessed Work UUID.
