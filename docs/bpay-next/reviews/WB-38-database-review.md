## Essential findings sent to root

1. **SNOOZE_CHECK refusals do not reach the new Worker contract.** In `0312...workbench_controls_v1.sql:36–45`, the new branch invokes the native context inside the existing outer exception handler at `:784–797`. A native stale/conflict/date refusal is converted to an HTTP-200 generic Workbench error envelope. Current Worker `broker/src/bpay-next-workbench.js:662–663` recognises named snooze errors only for a non-OK PostgREST response, then requires exact successful `{ok,kind,context}`. A refused Check therefore becomes RESPONSE_INVALID and loses its real reason. Re-raise errors for this exact new branch, or implement the same closed snooze failure shape at both ends. Preserve unrelated Workbench reader error behavior.

2. **Standalone physical Timesheet mapping is not a bounded, unambiguous physical-version point.** `0312...context_controls_v1.sql:32–41` accepts physical ID only, joins all Candidate Work/current-revision pairs and performs non-STRICT SELECT INTO. There is no viewed physical-version qualification or two-row ambiguity refusal. The core guarantees unique original_timesheet_id, not unique physical ID across every native revision (`03102026_1324...core.sql:115–129,142–168`). A non-STRICT SELECT silently chooses a row on multiple matches. Qualify the actual physical ID/version and candidate, reject ambiguity using a bounded lookup, and use the actual indexed original/current mapping or a minimal native physical-revision point index. Never substitute another original physical row or walk Candidate history.

3. **Many page receipt row bound checks the wrong JSON path.** `0316...snooze_many_receipts.sql:55` checks `result_body->'rows'`, while `0316...snooze_many_v1.sql:194–197` stores rows beneath `{result,rows}`. The CHECK evaluates SQL NULL for the actual envelope and does not enforce an array or its <=100 bound. Check the actual nested array type/cardinality and closed result size.

4. **New accepted scope/page receipts have no frozen-field/immutability guards.** The migration enables RLS and revokes browser/service table access, which is correct, but no UPDATE/DELETE/TRUNCATE guard is defined for the claimed immutable page receipts or frozen root/member identity/basis/child-request fields. Original 0255 guards protect native single control/event/ack receipts, not these new support records. Add only narrow guards for these card-specific support records: root frozen fields stay immutable; aggregate result is single-assignment; counters/progress reflect valid bounded outcomes; successful line state cannot be rewritten or retried; original page request/result is immutable. Permit the exact legitimate counter, aggregate and failure-to-success progress transitions.

5. **Retry and continuation validation still scan growing operation history.** Current `0316...many_v1.sql:102–104` finds a continuation by examining every prior page's JSON next_after_line_no, despite only a `(request_id,page_no)` primary key. `:114–116` finds <=100 failed retry line IDs by filtering all ordered root line records with JSON-array membership. These can walk arbitrarily many prior pages or successful members. Use an exact retained continuation/previous-page PK operand, and a separate retry query joining the bounded failed IDs to `(request_id,line_no)` primary-key points. Preserve native line_no keyset LIMIT100 for normal pages. No new action or protocol is required.

6. **New context count is multiplied through original single-child guard paths.** `0312...context_controls_v1.sql:163–164` counts every expense/mileage line in the revision for every Work scope/phase. MANY calls original per-line context, ACK/SET and metadata guards repeatedly. A <=100 page therefore repeatedly scans the whole expense scope. Keep the complete count where the public all-expense Check/root needs it, without adding that scope count to every EXPENSE_LINE PRE_SAVE authority call. This is a new read-cost regression in an otherwise point-based native owner.
