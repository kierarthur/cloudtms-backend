## Findings

No concrete type, NULL, cursor, byte-budget or allocation defect was found in the reviewed pages under their native typed scope and caller contract.

1. Every helper rejects a NULL or out-of-range limit and admits 1–100 source members per call. Prior-run pages seek `(pay_date, created_at, run_id)` and point-resolve this Candidate's Worker; they preserve the original prior-arrangement comparison using Worker identity and existing contribution presence. The source path has native `bpay_next_run_current_pay_date_idx` and the Candidate/Run worker point key. No Candidate-wide money SUM is introduced.
2. Precheck and staging seek the original frozen `(age_key, case_id, component_ordinal, component_id)` tuple. Original instruction uniqueness `(run_worker_id, preparation_revision, case_component_id)` makes component/period calculations disjoint. Counts and cursor update in the same transaction; a byte-limited exit leaves the next row outside the retained cursor. Terminal exhaustion checks exact native expected counts; more legitimate instructions continue through more pages.
3. The explicit ceiling is 65,536 encoded bytes. Input/native financial tuples are measured before proposed-row insertion and page counter mutation. An oversized individual tuple raises a named infrastructure error and rolls back the page; a cumulative overflow stops before that row. The prior-run and validation helpers preserve their own separate cursors. The helper return is a small typed metadata object. These facts close the page-bound design condition for the reviewed phases only.
4. Native instruction channels/VAT/amounts are NOT NULL and constrained; absent Draft results are refused explicitly. A present instruction-bound hold has the native all-or-none typed hold shape, exact instruction/result/Worker FK and unique ACTIVE instruction index. Missing hold means exact zero; missing capacity-use proof or incompatible prior result refuses before hold mutation. No historical NULL is priced into a new accepted result.
5. NET_DEDUCT calls only the original eight-argument 0290 kernel. Its capacity expression is the original Draft ceiling and period/component limits, plus Case capacity with previous staged release/reserve deltas and the current own hold added back. It never adds back future own holds. The Case carry captures revision/outstanding/active capacity, compares them on later visits and only updates proposed metadata. Non-NET instructions retain the original Draft financial tuple and totals. Live Case/component/period/hold/use rows are only read/locked; no active reservation or accepted result is changed.
6. Validation requires the exact STAGING fence and checks staged prior hold identity/amount, live Case/component/period revisions and ACTIVE use, Case carry snapshot, result sequence and total count. Own week contribution and gross/addition/cash conditions are checked before commitment. A missing native dependency cannot silently qualify: strict point reads fail, tuple comparisons use `IS DISTINCT FROM`, and schema non-null guarantees support the remaining numeric comparisons. Validation has its own bounded pass and then, when required, a bounded prior-run pass.
