## Remaining concrete findings

1. **D08 ALTER DEFAULT and material rail-key mutation are unchecked.** `assertProviderDefault` recognizes CREATE TABLE enabled-default and INSERT / UPDATE/MERGE enabled assignments, but an actual `ALTER TABLE private.bpay_next_rail_capability ALTER COLUMN enabled SET DEFAULT true;` is not rejected. Neither is `UPDATE private.bpay_next_rail_capability SET rail='PROVIDER' WHERE rail='CSV';` without an enabled assignment. The latter can carry an existing true CSV value into PROVIDER (e.g. after removing the disabled PROVIDER row); a database key collision does not prove the source guard. Classify the actual ALTER default and all material rail/default writes, or refuse them as bounded unclassified unless a proven off/approved nonprovider tuple. CREATE default-on false must remain allowed. INSERT ONLY and MERGE target forms should share the exact target classifier rather than another regex.

2. **D12 inner first-statement DDL is invisible to anchored heads.** `assertFrozenAuthority` scans extracted body statements but checks `^alter/^drop/^create` on the statement text. `DO $$BEGIN ALTER TABLE private.bpay_next_work DISABLE TRIGGER bpay_next_work_pointer_guard_v1; END$$;` yields a first inner statement starting BEGIN; no authority branch fires. New guarded DDL inside IF/LOOP or a routine body has the same seam. D09 has no special/dynamic violation for this static DDL, and original file byte/routine-definition equality does not detect changed trigger firing. Detect actual DDL heads within PL/pgSQL statement context, or refuse newly authored inner DDL unless the exact enclosing statement exists at F-01. Preserve genuine baseline DO owner/RLS/trigger construction.

3. **D09 dynamic schema-format exception is insufficiently bound for D12.** `schemaFormat` permits a fixed FORMAT pattern if *any* FOREACH v_table ARRAY exists anywhere in that body; it does not bind the real array, loop membership, callback or entire enclosing source to F-01. A new loop over a frozen table with `execute pg_catalog.format('create trigger %I before update or delete on private.%I for each row execute function private.bpay_next_work_pointer_guard_v1()',v_table||'_immutable',v_table)` receives the exemption, while D12 sees EXECUTE/FOREACH rather than CREATE and misses new frozen callback binding. The similarly permitted dynamic owner/RLS commands can target frozen tables. The safest small fix is exact F-01 enclosing schema-loop allowance (including array/callback/format), or a finite parsed target expansion against the existing frozen policy; not a format-string-only or any-array exception. Owner-only CURRENT_USER policy FORMAT similarly needs its actual relation scope/frozen-security effect classified, not generic SQL permission.

4. **Approved nonprovider seed shapes should remain truthful.** EX-47 names CSV/EXTERNAL/SIMULATED/PROVIDER. Current tuple allowlist contains only CSV/EXTERNAL/PROVIDER and therefore rejects even SIMULATED=false. Permit exact disabled SIMULATED if used by the actual EX-47 owner; SIMULATED availability/enabling remains separately controlled by the TEST marker. This is a future declared schema compatibility point, not permission to build EX-47 here. Existing CSV/EXTERNAL=true + PROVIDER=false mixed tuples and disable UPDATE are appropriately permitted by the new per-statement code. Additional authority strings/layouts currently fail unclassified, which is preferable to pretending to infer them; widen only when the actual card’s finite seed requires it.
