# PF-08 phased E4/E5 design review

**Verdict: required design amendment identified; no product/A4/runtime approval.** Review is read-only against current native sources and owner E4/E5 instructions. BD124's original metadata-only/PREPARING interpretation is insufficient for exhausted genuine financial preparation failures. Use the phase split below rather than one blanket PREPARE transition. Five consecutive failed STEP attempts at one exact retained checkpoint remains the operational ceiling; successful validated progress resets that count. CLAIM contention, predecessor waits, continuation-send failures and unconfirmed outcomes are not definite failed economic attempts.

## Minimum phase-specific transition

| `NEW`, `PINNING`, `RESERVE`, `ALLOCATE`, `FINANCE_ALLOCATE`; genuine failed economic preparation, not an E2 omission | Retain the unfinished job/checkpoint; move its actual worker from PREPARING to REVIEW once, with finite operational attention evidence. Do not mark job DONE or call the projection-begin owner, which overwrites the checkpoint. | Atomically clear only this attention state; restore worker PREPARING, debit review/credit preparing once; advance **execution** preparation revision exactly +1 before any resumed hold-changing step. | Ordinary `WORKBENCH_WORK` / `WORKBENCH_CASE` after financial outcome | Keep the actual READY or REVIEW financial outcome and existing counter bucket. No new economic execution revision or hold change merely for projection. | Existing preparing→ready/review transfer has already happened. No second debit/credit. Keep parent PREPARING until projection completes through its original owner; do not exempt unfinished projection as completed economic attention. |
| `WORKER_RELEASE_WORK` / `WORKER_RELEASE_CASE` / `WORKER_RELEASE_FINAL`, or WORKBENCH projection with an exact RUNNING RELEASE / PROJECT binding | Preserve native CANCELLING during release and CANCELLED during its original final projection. **Origin must be tested before phase alone:** current `private.bpay_next_prepare_projection_page_v1` first routes WORKBENCH phases into `private.bpay_next_project_worker_release_page_v1` when the same job has `action='RELEASE', status='RUNNING', stage='PROJECT'`. That is cleanup projection, not the ordinary second row above. Other job kinds, whole-Draft expiry/discard and their native retirement retain their owning recovery. Never let a queued retry bypass an active expiry/discard fence.

The five-attempt attention mechanism can carry operational metadata for these classes without a new status framework. The failure/retry owner must recheck the exact kind/job/run/Candidate/module epoch/lease epoch/phase and phase-specific cursors under the original module→run→Candidate→job order. Replayed FAILURE for the same attempt increments once; a committed advanced/DONE result wins. Unknown STEP outcomes keep their exact original request and active lease until existing recovery proves current truth, so a timeout cannot manufacture REVIEW or clear a live lease.

Preserve the original job/run resolver.
4. Same file `:6771–6804`, `private.bpay_next_worker_execution_guard_v1`, also authorizes +1/active-job changes only through the original DR05 request. Add the same exact operational-retry receipt branch, tied to old/current worker, run, Candidate, original input job, captured revision, expected/target execution revision and current active job. 5. `11102026_0814_banking_pay_next_preparation_discard_v1.sql:3913–4002`, current projection owner, finalizes job and worker-action request then calls native Review. 6. Same file `:2801–2897`, progress owner, reads stored ready/review/removed/preparing counts and derives pending; expiry/discard have their own request counters. Preserve the whole-scope conservation and `preparing≤pending` invariant. Operational attention count is a separate overlapping fact, not an extra financial bucket to add to those totals. UI must not infer attention-row counts from one loaded page.

## Presentation and later DR-15 join

PF-08-D03 remains the existing DR-06 window. Show the actual Candidate, operational **Needs attention** state/reason and quiet **Try again**, using the original same-request command journal. Financial failure REVIEW, ordinary projection attention and unfinished cleanup must have distinct plain reasons; no raw phase/code/job/revision vocabulary. A disabled action needs its current reason on screen. Processing requested is the result of acceptance; Prepared/Paid is not inferred.

Later DR-15 should consume the same typed native attention evidence alongside completed financial REVIEW outcomes. E2's automatic Not in this Draft distinction remains intact: the existing six-code branch in `begin_prepare_projection_v1` starts native system RELEASE for changed/not-approved/query/no-payable work. PF-08 must not convert those into staff-resolvable preparation failures, remove their mandatory release or fabricate returned-work completion. DR-15's full identity/list/reference presentation remains its own card; no additional screen or live Work recapture is proposed here.

Current Worker `broker/src/bpay-next-job-step.js:298–311` already distinguishes projection worker READY/REVIEW/CANCELLED, release CANCELLING and terminal CANCELLED. Current FE progress counts and review handoff depend on real run/worker status. Extend their closed operational-attention contracts only where the typed native owner above requires it; do not weaken ordinary phase/result validation.
