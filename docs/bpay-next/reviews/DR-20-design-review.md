## Concrete design assessment

The proposed successor only to `public.bpay_next_enroll_service_v1()` is narrow card-required support: DR-20:534 explicitly requires database enrollment pages to create the worker jobs in a few steps. Reusing unchanged `private.bpay_next_enroll_one_v1()` up to 20 times for one original sealed selection makes that a bounded metadata page. Twenty separate Worker RPC calls would reduce delivery turns but would not itself meet the database-page clause. The updated design distinguishes those cases; no new command/action/input/store, money owner, producer, Candidate inventory or queue configuration is required.

Exact current owners: public enrollment service `11102026_0541_banking_pay_next_enrollment_epoch_fence_v1.sql:5–60`; private enroller `11102026_2041_banking_pay_next_case_pause_v1.sql:545–712`; financial service `12102026_0016_banking_pay_next_stale_snooze_publication_v1.sql:739+`; native financial queue `broker/src/bpay-next-financial-queue.js:151–185`; enrollment receipt validator `broker/src/bpay-next-runtime-rpc.js:223–237`; background enrollment/publisher `broker/src/bpay-next-background.js:27–40`. ## Required exact implementation boundaries

1. **One command only.** Freeze the first native next command/sequence under the original enrollment clock. Batch only its genuine original RunCommand, PREPARE kind, current module epoch, Run PREPARING and selection SEALED, command ENROLLING, with no OFFICE worker-action request or expiry/discard fence. Here SEALED describes the selection: the command stays ENROLLING until its last member. Once the clock advances or that command completes enrollment, stop before another global private call can select the next agency command. Other kinds, OPEN waiting, retired metadata and OFFICE reprepare/release retain one original call.
2. **Existing lock order only.** Public0541:17–27 retains module SHARE → enrollment-clock UPDATE; private2041:562–569 repeats those original locks and locks the next command. Its original sealed PREPARE branch671–712 takes Run SHARE NOWAIT, reads one frozen selection member, inserts one command member/job, and increments the existing counts/clock. It adds no Candidate business/Work/Case lock or financial mutation. Existing FK key-share checks remain. Run NOWAIT is essential because seal/expiry take Run before command; do not replace it with a blocking lock or wrap another financial kind in the batch.
3. **Whole-page failure receipt.** Preserve one protected subtransaction over all page iterations. Any exception rolls back every inserted member/job/count in that page; reset PL/pgSQL jobs/scalars explicitly before the original blocked receipt (`progressed=false`, original clock, NULL scalar job fields, `jobs=[]`). A variable can retain rolled-back UUIDs after an exception. Do not return those IDs, retain a partial prefix under a false no-progress receipt, or clear the original command error marker on failure. Genuine zero-job clock advancement remains progressed=true with an empty array.
4. **Closed additive jobs receipt.** Add at most 20 unique native `{job_id,job_kind,job_status}` entries; scalar job fields equal the final entry, or all are NULL for an empty array. Every READY identity must be awaited for durable `{id,kind}` publication, including all entries before the final scalar. DONE entries cause no financial work. Update the exact runtime parser and every existing enrollment caller together; the current validator and background currently accept/publish one scalar only. Unknown enrollment reply remains uncertain metadata and native recovery finds committed READY jobs; it is not an empty successful page or a reason to repeat economic input.
5. **Fresh owner per STEP.** Financial service0016:1254–1262 yields its own validated nonterminal page to READY and clears the nonce. Thus every additional page needs fresh CLAIM and that returned exact phase/cursor/nonce/owner tuple. The 16-page/10-second limit bounds new work starts, not a hard wall-clock or Run size. If CLAIM already acquired a lease, perform its original bounded STEP/failure handling even if the soft deadline or phase exclusion is reached. Never reuse the preceding nonce or adopt another active lease.
6. **Cleanup stays original.** Normal extra work is limited to the finite original preparation/projection phases; expiry/discard and non-PREPARE kinds keep their existing single-page handler. A first claimed WORKER_RELEASE phase needs its original one page, then stop. Shared WORKBENCH_WORK/CASE can also dispatch release PROJECT (`2259:1742–1744`); CLAIM does not expose its action (`0016:1081–1089`). After its mandatory first STEP, the existing CANCELLED worker result must stop extra looping, while READY/REVIEW ordinary projection can continue. No new discriminator/reader is necessary.
7. **Wake/ACK ownership.** Additional accepted-request work must qualify positively accepted SEAL_ENQUEUE, not merely the wake header, which is also used by other accepted actions. Original durable ENROLL wake remains the fallback. Publish every READY identity before optional inline work; a competing queue CLAIM legitimately stops the inline attempt. Preserve exact PF08 rollback/unknown failure handling, durable deferred/attention state and awaited continuation before ACK. At most two distinct jobs may be in flight per accepted task; this is not a global concurrency guarantee across requests/queue consumers.

Root's concrete chosen limits are <=2 accepted-SEAL enrollment pages, <=2 concurrent original PREPARE jobs, <=16 STEP pages per job and a shared 10-second soft new-CLAIM/new-enrollment start budget; normal queue PREPARE can use the same 16-page/10-second bound, other kinds one page. Each RPC keeps its original eight-second error deadline. Completed metadata jobs cannot make a financial Claim before the native original command admission allows it; all original private admissions remain authoritative.
