## Findings requiring closure

**H01 — deadline leaves outstanding/late reads insufficiently cancelled.** `readWorkbenchJson` checks the abort signal before `reader.read()` but registers no abort listener to cancel that pending read. After an awaited read resolves it does not recheck abort before accepting `done` and parsing. The sender also does not check/cancel a late Response immediately after `workbenchRpc` returns. The handler's Promise race gives the caller an 8-second refusal, but an upstream implementation ignoring abort can retain a reader or parse a later body. Add narrow abort-driven `reader.cancel()`, signal checks after each read and before parse, and cancel a late response body before parsing. Preserve one RPC/no retries; no background work or new lifetime framework is needed.

**H02 — legal unknown Candidate amount disagrees with amount-sort cursor validation.** Current 1520 SQL uses `s.amount` for AMOUNT ordering and key, but returns row `amount=null` when `unknown_amount_count>0`. Worker `rowKey` uses `row.amount` and `validKey` requires decimal text, rejecting such a legal unknown row as RESPONSE_INVALID even though the server key is populated. Match one explicit named sort-key contract across SQL/Worker/client, preserving nullable unknown displayed totals; alternatively refuse an unsupported ordering as a defined typed error before producing a success page. Do not silently coerce the unknown amount to zero. SQL/projection sort changes are in progress, so recheck fresh source before closure.

**H03 — response validation does not enforce the explicit no-hidden-zero aggregate contract.** HEADER/CANDIDATES shapes allow any nullable decimal independently of `unknown_amount_count` and `unknown_selected_amount_count`. A row with unknown count positive and `amount='0'` currently passes. 1520 explicitly returns null for all ordinary aggregate amounts whenever unknown_amount_count is positive, and null selected amount when unknown_selected_amount_count is positive. Validate those finite native null/counter relationships (and `has_deduction` against its exact native count); no calculation or inferred economic result is needed. This is a malformed-response refusal, not a change to SQL money ownership.
