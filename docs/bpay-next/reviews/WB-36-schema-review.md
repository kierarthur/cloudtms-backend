## Findings

**WS01 — Owner mapping policy precision.** The initial dynamic DO `owner to postgres` literal was outside the release mapper's exact dynamic allowlist (`cloudtms-db-release-lib.mjs:338–353`) and static owner regex (`121`); root already changed these to explicit static owner statements, closing that part. Remaining policy clauses still say `CREATE POLICY … TO postgres`. `mapLogicalPostgresAclGrantees` (`19–38`) only processes GRANT/REVOKE/default privileges, not CREATE POLICY. Thus CURRENT_USER installation leaves the policy attached to logical `postgres`, rather than the actual logical-owner-mapped repository owner. Use the actual `CURRENT_USER` policy target or equivalent narrow native owner statement, preserving revoked service/browser access; no generic dynamic mapper exception is needed. Owner bypass may make current reads work but does not establish the claimed actual service-owner policy.

**WS02 — Close the shared scope tuples, not only each UUID.** As drafted:

- Snooze has independent Candidate, work, revision, physical, segment/expense and Case/Case-component references. These permit a Candidate-A snooze naming Candidate-B work or a component belonging to another Case. Existing typed targets include work `(id,candidate_id)`, revision `(work_id,id)` and Case component `(id,case_id,candidate_id)`; use those actual tuples or exact mandatory insert qualification.
- Approved segment's shift-detail UUID can name a different approved line than its revision/line/component FK. Captured run-segment `(captured_revision_id,approved_segment_id)` does not bind its asserted `segment_key`. The parent-attribution row's `approved_line_id` likewise is not tied to the approved segment. Exact originating shift/segment/line identity must be qualified by native composite FK or required immutable insert guard.
- Origin share independently binds a hold UUID, `(run_line_id,work_id,component_key)` and `(run_work_segment_id,component_key)`. A row can use a different run's hold or a captured segment of another work while asserting its own work/segment strings. Bind the actual hold/run-line/captured-parent work/component/segment tuple. Existing 2010 provides hold/effect `(id,work_id,component_key)` targets; additional redundant native unique keys are small schema support if required, not new authority.
- Effect share has only `effect_id→id`, with unbound asserted work/component/segment. Effect-origin membership likewise binds two independent UUIDs without proving the same actual work/component/segment or the exact original hold share. Qualify those shared native identities before an effect row can claim/consume a share.

The coming private guards may intentionally perform semantic joins; if so, record and implement each exact insert qualification before this subset is marked safe. Owner-only ACL does not replace native common-scope binding. This finding does not require broad historical proof or a new producer protocol.

**WS03 — Explicit scope/operational NULL shapes.** Current boolean equivalences for required CASE/SEGMENT/EXPENSE_LINE IDs are NULL-safe because they use `IS NULL`, which is good. They do not forbid every foreign optional field: CASE may carry unrelated expected revision/physical/component data, non-CASE may carry arbitrary `case_kind`, WHOLE/EXPENSES_ALL may carry arbitrary component_key, and CASE's actual kind may be NULL. Define the exact finite scope disjunction or mandatory guard for required and forbidden fields; tie Case kind/component to its actual parent. Warning ack also needs finite supported scope, valid module epoch/control version and bounded native scope identity, with its optional expected revision shape bound to that scope. The actual 30-minute equality and consumed-ID/time pairing are sound, but alone do not make an exact valid token. `run_segment_capture` currently accepts partial nullable cursor tuples (for example work ID with NULL segment/component); declare all-NULL versus complete native cursor shape and positive/bounded key constraints or enforce them in its operational guard. These are current schema/guard requirements, not future action attachments.
