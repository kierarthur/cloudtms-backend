## Concrete findings

**J01 — shared-handle late reply, closed in the fresh source.** Initial `busy` belonged to each factory handle while journal state was shared by namespace. Two handles could dispatch/retry the same pending page; after one reply and a subsequent page, the late reply could clear the newer pending bytes and regress counters. The fresh shared namespace operation object covers mutation/retry/readback and reply adoption compares retained action/bytes/SHA to the still-current pending request (`:447–459,494–509`). This closes that concrete duplicate-reply race.

**J02 — stale completed handle can erase a new journal, open.** `acknowledgeComplete` qualifies its captured old state/operation but calls `storage.removeItem(key)` before proving those captured objects still own the current namespace (`:524–530`). After a first acknowledgment removes the Map entries and a new submission starts under the same namespace, calling the old handle's method again can delete the new pending journal from storage. The subsequent conditional Map deletes do not repair lost durable bytes. Require current Map state and operation identity before any storage removal or store acknowledgment; retire the old handle after successful completion. This is a finite existing-key lifetime guard, not a new protocol.

**J03 — restored/failed namespace paths bypass the bound, open.** The256 limit is only inside the brand-new journal branch (`:486`); a restored persisted journal can be inserted beyond the bound. In addition, `choiceSubmissionOperations` inserts its entry before failed validation/size checks (`:458–459`), allowing failed namespace attempts to accumulate operation entries independently of the declared cap. Apply the same admission bound before inserting any new namespace, including restoration, and do not retain an operation object after a failed constructor. Existing live entries must remain usable and must not be evicted.

**J04 — restored journal accepts inconsistent acceptance/command tuples, open.** `valid` checks shapes but permits a COMPLETE/READBACK/SUBSETS state with `create_receipt:null`, and does not bind a saved CREATE's command/descriptor or saved SEAL's command/counts to the journal's original identities (`:461–481`). For example, the shape-correct initial state with phase changed to COMPLETE passes validation and can acknowledge/discard the local choice generation without a CREATE/SEAL receipt. A restored pending CREATE with the same run but a different valid command/descriptor is also admitted to `retry`; it bypasses the guards used by `mutate` and can be sent before later adoption fails. Validate these finite correlations on restore and before dispatch: CREATE exact run/command/descriptor; post-CREATE phases require its original receipt; empty/nonempty phase consistency; READBACK/COMPLETE require the original matching SEAL receipt and sequence; saved SEAL exact original command and submitted page/count tuple. Preserve unknown pending bytes by refusing invalid state rather than replacing identities. No certificate, new financial authority or parked accepted-input mechanism is needed.
