## Essential findings — first pass

1. **Per-Case work is not bounded (`:116–173`).** `case_list_row_v1` loops every Case component without LIMIT/cardinality guard, and performs period/rule/snooze/valuation work for each. The 16KiB output bound and 100-Case outer seed do not bound this SQL work. The independent design explicitly requires a finite child path or honest gap. Add a finite native child seek/check before evaluating each child; retain the Case row and honest unknown/category gap if an unsupported oversized membership is encountered rather than silently summing a prefix. Scope-specific active snooze uniqueness can be relied on only after verifying the existing index/constraint.

2. **Five DESC creation index pathkeys disagree with SQL.** Migration `:21,25,27,29,31` use `created_at_utc DESC` (default NULLS FIRST), while reader `:280,287` explicitly orders that term DESC NULLS LAST. The preceding is-null key makes the resulting data order equivalent, but does not make PostgreSQL's index pathkeys identical or prove a fully matching Index Scan. Use explicit NULLS LAST in those five DESC date index terms; the ASC index already has matching default placement. No execution/performance claim is made here.

3. **Metadata hook performs full per-Case recomputation instead of the approved indexed set update (`:49–52`).** Each metadata update loops all historical Case IDs for the Candidate and rereads frozen origins, rules and public Candidate data per Case, even for bookkeeping-only metadata changes. BD115's peer condition permits an indexed set-based Candidate-name/reference fan-out with its actual write cost stated, not repeated financial/origin recalculation. Replace this loop with the minimal key-column UPDATE for relevant name/reference changes; target/control changes need existing-revision invalidation, not Client/rule rederivation. Do not introduce a new task/protocol to solve this.

4. **Selective list predicates are applied before the raw ordered LIMIT (`:296–300`).** The six global ordering indexes do not include Candidate/Client/subtype prefixes; the scope indexes are only `(scope,case_id)`. Thus a Candidate-filtered Created/Type list can require filtering the entire global ordered index or sorting the full Candidate scope before LIMIT. Returning at most51 rows does not prove a bounded raw scan. Either use actual matching scoped seek indexes or apply these filters after the bounded raw native key window, advancing the scan cursor over exclusions as the existing post-filter path already does. Summary's Candidate/Case-ID prefix is a different, potentially matching path. No false universal index-coverage claim should remain.

5. **Byte budgeting excludes potentially large cursor/envelope (`:219,314–344`).** The 2048-byte fixed allowance is smaller than an allowed 8192-byte Candidate sort value plus context/filter/JSON envelope. Ten or more large but valid rows can fit the row-array budget while the actual final reply exceeds120000 bytes once `next_cursor` is appended. Reserve the actual bounded cursor/envelope or construct/check the final reply and back up the last included raw member consistently. Do not mark skipped bytes as scanned/complete. Current rollback-to-previous-key logic is otherwise the right conservation mechanism.
