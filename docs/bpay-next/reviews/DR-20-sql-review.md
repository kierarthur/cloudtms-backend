## Initial verdict — OPEN

An expiry/discard transaction can finish after that qualification snapshot but before private2041 takes Run SHARE NOWAIT. The unchanged native owner can then legitimately observe CANCELLING with its exact fence and insert PREPARE/DONE jobs in EXPIRED/DISCARDED phases (`2041:671–699`). Public0945 retains the earlier true `v_batch` and can call it up to 20 times. Its valid committed multi-DONE receipt is rejected by the new runtime decoder (`bpay-next-runtime-rpc.js:236`), which rightly requires every multirow job to be PREPARE/READY. This also violates BD140's one-call cleanup exclusion.

Minimal correction: after reading each actual returned native job, permit extra iterations only if it is PREPARE/READY. A first DONE or other-kind result must finish as the original one-call receipt. Once a first READY original member is returned, the unchanged private owner holds Run SHARE through this bounded metadata transaction; expiry/discard cannot change the Run while subsequent members are enrolled. Do not weaken the decoder to admit cleanup batches or change the private financial/enrollment owner. Reported to root before loading.
