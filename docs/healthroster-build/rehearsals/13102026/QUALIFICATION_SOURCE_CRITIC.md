## Finding 2 — P1: SEND_7 lock observation lacks the database namespace

`Q/QUALIFICATION_SCOPE.sqlinc:130-132` and `196-198` verify an advisory lock's key `(20261013,1)`, mode, grant and supplied separate PID. They omit `pg_locks.database`. Advisory lock keys are database-scoped, while `pg_locks` exposes locks across the cluster. Therefore a matching lock in another database can satisfy this source predicate even though it is not the SEND_7 turn on `cloudtms_test_clone`.

The predicates also prove only that a supplied PID holds a matching lock; they do not establish that the caller owns the corresponding turn connection. Root must never populate that PID from another task's observed lock.

**Required correction:** bind both predicates to the current database OID. The root harness must obtain the PID from its own successfully acquired, retained turn connection, keep that exact connection open through before/after fingerprints and fresh rollback verification, and release it after one short trial. Cover a matching other-database lock, a foreign turn PID and a lost turn with refusal proofs. No new durable database object or grant is required. This is a source predicate finding, not a claim that a conflicting runtime session was observed.
