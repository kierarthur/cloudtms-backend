This is a source-only transaction-fence design for independent review before implementation. No schema, SQL definition, role, setting, database, runtime or native schedule has been changed. The accepted classification30/dd09 checkpoint remains immutable. Its current source closure does not qualify hidden RR.

A real row update is the necessary shared conflict. PostgreSQL17 explains that an RR transaction cannot update a row changed after its snapshot and must abort with serialization failure; READ COMMITTED INSERT ON CONFLICT DO UPDATE can instead update a conflicting row that was not visible to the command snapshot. PostgreSQL's executor also explicitly checks conflict-tuple visibility under transaction snapshots. These facts support the mechanism, but do not prove CloudTMS writer coverage or an installed native result ([transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html), [INSERT](https://www.postgresql.org/docs/17/sql-insert.html), [PostgreSQL17 executor](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/executor/nodeModifyTable.c)). The actual installed PG build and conflict behavior remain native gates.

The simple family-row option can close the specific hidden-WAITING counterexample only when every writer independently derives the same existing immutable T0. SEND touches the T0 fence before inserting WAITING/P0. A creator performs an unconditional insert-or-physical-update of that exact row before business DML, irrespective of whether its snapshot sees a request. An older RR then conflicts even if its request census is empty; RC holds the fence until transaction end and reruns the actual native clock/request checks after acquisition. A lock-only operation, DO NOTHING, a conditional no-op UPDATE, or a check gated on visible WAITING is insufficient. No row should be deleted/recreated as an unlock operation.

The exact current0519 source shows why that option is not complete for all71 writer candidates. Reference triggers accept raw OLD/NEW timesheet UUIDs; invoice references also accept OLD/NEW booking text and can have no FK. A new P0 UUID can be supplied to a writer whose older snapshot sees neither P0 nor its request; canonical-T0 lookup then has no row to follow. The Candidate trigger first scans visible timesheets and restricts them to a signed precursor or visible WAITING request. A Candidate alias/rank mutation can have no discoverable family if the relevant physical/signature rows were committed later. Booking-only invoice lines and raw NULL/foreign-Contract siblings cannot be excluded merely because a Contract or Timesheet join fails. Therefore a one-family-row design must not be called complete while any of these intent arms depend on snapshot-visible request/physical lookup.

The concrete alternative for review is a small owner-private concurrency-token table with a canonical-family row plus exact native physical/booking/occupant identity tokens. These are serialization identities, not economic keys, business history or a U3/Checklist ledger. A token records only its kind and the exact existing native identity; it supplies no pricing, subject, readiness, status, actor or ownership authority. No request-state/economic selector is added. It is used only by SEND and the four actual existing-table creator guards, never by read projections. Names and physical schema are deliberately not authored until root accepts the design.

SEND must touch the family and existing native identity tokens before its first affected unit mutation, including native replacement-week allocation, then touch the actually assigned replacement UUID/booking tokens before publishing WAITING or creating P0. Current SEND already assigns replacement_timesheet_id with gen_random_uuid before inserting the request; that genuine owner-produced UUID can be fenced without inventing a receipt identity. Current native leg creation explicitly writes parent_timesheet_id=root_timesheet_id and uses the stored assigned UUID. This token preparation must preserve all current replay/actor/state admission, native Candidate/I-1 order and real lineage creation. It cannot move a financial or invoice decision to the token table.

Each creator collects OLD/NEW raw tokens before any visible-request census or precursor test. It touches a sorted, deduplicated token set with unconditional INSERT ON CONFLICT DO UPDATE that actually writes the conflicting tuple. Its private write is subject to the same bounded nonwaiting behavior as the current native owner: preserve/restore lock_timeout, refuse busy acquisition, propagate 40001 or55P03 through the actual atomic owner and roll back the whole unit. A caller must not catch the conflict in a subtransaction and continue business DML. The table must have no trigger that suppresses the physical update. The exact ordering relative to already-held native Candidate/family/invoice rows requires independent lock-order review; adding a token before a BEFORE trigger does not magically move the table's initial UPDATE row lock. This must be qualified rather than asserted.

After acquisition, RC rereads the actual native request, full A0 clock, source configuration, signed witness, actual family/reference/booking/Candidate and immutable scope using existing owners. The token never grants admission. An RR snapshot established before SEND is expected to fail on the shared token before business DML; if no such conflict exists, the native guard must still validate its actual scope. Any unproved relevant scope remains refusal/WAITING. Ordinary writers still use their existing business rules; a NULL timesheet_id plus NULL booking with no actual native family/occupant identity must not be relabelled an A0 reference. Native standalone NULL Report/invoice lines require their genuine existing owner proof, not a blanket NULL ban.
