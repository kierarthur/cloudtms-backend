# V6 global manager contact timing source proposal

This is the bounded Health-owned source for CONTACT_PAUSE_SPEC “Closed global contact timing extension” and “Native first-delay precedence and settings round-trip — SOL-16”. The retained authority filename contains `v5-amendment`; its text was reconciled with the final V6 release. It does not reinstate a withdrawn draft. SOURCE_INPUTS records the actual saved native owners read from I2 and Office. No root shared file, Office checkout, Banking component, database or provider was changed by this proposal.

The existing global singleton and GET/PUT `/api/weekly-source/v1/settings/global` remain the owners. Five columns add direct first delay, an ordered 0–10 follow-up vector, recent completed weeks and maximum work age. Defaults are 0 HOURS, one MANUAL follow-up after 2 CLIENT_WORKING_DAYS, 1 completed week and 14 days. Interval bounds are 0–8784 elapsed HOURS or 0–366 calendar/working days for first delay; follow-ups require at least 1. These are finite input bounds, not an additional financial or contractual cutoff. Existing worker/reminder/deadline/digest/cooldown/link/automatic-actor values survive unless their existing controls are edited.

The existing save owner now requires `request_id`, canonical string `expected_settings_version`, and closed settings. It checks current active admin/deployment before replay. A singleton row lock serializes journal creation and CAS. Same request/actor/deployment/digest returns the exact accepted response; an altered request conflicts; a different stale request conflicts. An unchanged accepted save journals its receipt without incrementing the version. Versions remain SQL BIGINT decimal strings throughout SQL, Worker and Office. The new immutable receipt table has FORCE RLS and no browser/service-role table grants. Only the existing two public RPCs retain explicit service-role EXECUTE; private readers are owner-only.

`forward/settings.js` is a complete replacement proposal against the exact Office reference. It preserves canonical `manager_digest_minutes=137` and `manager_manual_resend_cooldown_minutes=11`, strips both stale aliases before PUT, displays all new controls and the server cutoff explanation, and retains exact request identity/body through a lost response. A changed edit after uncertainty asks for a fresh read. Fresh server values replace old cached draft/default aliases. The Worker module rejects duplicate JSON keys, unknown keys, malformed vectors/revisions and browser actor/deployment facts, and decodes the exact current response. The `.d.ts` supplies the additive row/DTO schema; no pre-existing generated TypeScript database owner was found in the actual JavaScript backend.

Native13 assigns each membership its actual initial purpose before hashing/generating due events. Exact current resolved pending Source rows which match actual declared Timesheet clocks use MANAGER_DIRECT independently of a neighbour requiring a worker answer. It uses the existing current-source-row reader and actual candidate Timesheet week ending, without using the absent NHSP comparison system-clock fields as a match shortcut. Direct due is genuine eligible start plus the configured first delay; candidate-first T6 remains its actual generation start plus the existing digest interval, and its T12 remains its actual deadline. No worker clock is changed. The existing due-event trigger hash tags these new initial purposes; native11 enforces the matching incident scope. Legacy untagged all-responded/requested-week/manual due events retain their prior semantics. No new event store, tranche, sender or capability phase is created.

`private.weekly_source_manager_interval_due_v1(uuid,timestamptz,integer,text)` uses elapsed HOURS and London calendar arithmetic. Working days skip Saturday/Sunday and dates in the actual Client effective `values.bh_list`, whose existing core already normalizes the configured `bh_list UNION bh_feed_list`. No regional/calendar copy or new feed is added. Calendar failure holds evaluation. Shared London boundary handling preserves real start seconds across DST.

`private.weekly_source_manager_followup_timing_v1(accepted_membership_id uuid,at_utc timestamptz)` reads the actual immutable accepted contact membership and verifies its incident/episode/work/candidate/client/purpose/budget lineage. It derives the latest consecutive accepted ordinal and next vector step from the preceding accepted timestamp. Unsubmitted, skipped and deferred rows do not start a clock. It returns MANAGER_FOLLOWUP_TIMING_V1 with string policy revision, exact logical key, last accepted time, next ordinal/mode/due, routine age/week classification and `requires_current_start_admission=true`. It never allocates a send or returns final permission. MANUAL is an Office step; it cannot become automatic merely because due time passed.

The final repeatable must reapply the same two global owners after older native06 definitions. Office source is supplied here for the Office owner to integrate; this lane did not edit that checkout.

Automatic follow-ups therefore require root's current accepted-budget/render membership composition to consume the exact timing reader. Creating another old tranche or bypassing accepted ownership would be wrong. Preserve earlier accepted links/history and derive the next send ordinal from actual receipts.
- At final START, re-read current timing policy and apply completed relevant reports, current declared work/need/replies/recipient, no-pay/denied-final decisions, pause, age/recent-week routine limits, actual hard Client cutoff and budget under the common sorted scope locks. Saved event times/browser values are advisory; a later policy change cannot be bypassed by an old due event.
