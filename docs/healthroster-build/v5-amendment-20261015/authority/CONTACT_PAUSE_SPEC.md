# Contact pause and timing: exact implementation contract — V5

Required new implementation; not installed or remotely tested. The selected worker+client checking PAUSE covers report/Timesheet checking and related client-scoped worker feedback; its exclusions are authentication/security, general Rota, provider, bank-payment and remittance communication. These PAUSE exclusions do not limit global quiet timing. GLOBAL QT applies to every Candidate native push at the existing central queue/final APNs/FCM sender, including current and future producers. Quiet delays only the native alert: email, in-app access, authentication/security operations and worker clocks remain available. No Rota, OTP, remittance transport or parallel queue is commissioned here. Parent invariants PA-01–05/QT-01 and UI_POLICY_AND_COPY.md control this contract. No email, push, drain or database call was executed for this design.

## Scope and clocks

The durable key is environment + agency + **candidate_id + actual client_id**. Contract, manager recipient, source group and week are not the pause key. The three choices are WORKER, MANAGER, BOTH. MANAGER covers all ward managers and Temp Staffing/correction recipients for that worker at that client, not every worker sharing an address. BOTH is two independently guarded audience bits. Pausing Taylor/Northbridge leaves Taylor/Southbank and Alex/Northbridge unchanged. Pausing only WORKER leaves independently justified manager requests available; MANAGER leaves a necessary worker question available. Never infer the second audience should be paused from a grouped email.

Expiry is the next strictly future Monday 00:00 in Europe/London computed from the server's current instant and existing London date/calendar helper. Store the resulting UTC instant and display local exact date. Not `now +168 hours`. Fixtures: Thu 15/10/2026 09:00 BST → Mon 19/10/2026 00:00 BST =18/10/2026 23:00Z; Mon 19/10/2026 00:00 BST → Mon 26/10/2026 00:00 GMT =26/10/2026 00:00Z (169h); Fri 27/03/2026 → Mon 30/03/2026 00:00 BST =29/03/2026 23:00Z. At `now >= paused_until_utc` the pause is inactive. Changing clock time in the UI never chooses expiry. Saving on Monday 00:00 targets the following Monday. Existing holiday configuration does not postpone Monday expiry.

An unpublished worker request held by pause gets no activation/deadline merely for waiting. Activation occurs once on the next still-eligible permissible release, independently of push quiet timing. Existing active questions retain their real start, reminder schedule and response deadline. Pause does not extend cutoff, create non-worked evidence, reset a reminder allowance, or overwrite a late reply. Existing question screens, link access, signed documents, worker replies and manager partial replies remain usable. Expiry is lazy-correct at every predicate plus a bounded scheduler wake; no timed sleeper or held database connection.

## Submission race and receipt protocol

Remote sending cannot be recalled by a database lock. Prepare freezes recipient/content/member revisions. **START is the linearisation point**, in the final existing runtime immediately before its provider call: the new service-only start RPC locks every included scope, rechecks epoch/current eligibility, then records STARTED and returns a single attempt permit. PAUSE locks the same scope rows and increments their admission-blocking revision. Whichever transaction commits first owns the race. A start committed before pause is already admitted and may finish after pause, even if the network call begins slightly later. The pause acknowledges immediately when future admission is blocked; it does not wait indefinitely for a provider receipt. Copy: **Messages paused until … One message had already started; its result is being checked.** Show the exact audience/recipient/time/shift membership beside that known in-flight message. Accepted result displays **Sent** with actual time; never claim recall.

The existing manager runtime (`deliverManagerTarget`) and final Candidate broker `DELIVER` handler consume the new permit once. Repeated START of an already-STARTED attempt returns a read/check result, not permission for another provider call. A crash or lost result between START and provider return is **AMBIGUOUS**, including a crash before a network call can be proved. APNs/FCM do not provide a guaranteed lookup/idempotency contract for this attempt; do not invent one. Existing documented email idempotency may be used only when its real provider supports it. Automatic retries continue only for a proved no-submission/transient rejection; uncertainty never authorises a new send. A proved no-network pause/quiet deferral is NOT_STARTED and spends no provider attempt or accepted-send budget.

Exact new command `CONTACT_SEND_RESULT_REVIEW` → service-only `public.weekly_source_contact_send_result_review_v1(jsonb)` accepts exact delivery/permit ID, request ID, expected attempt version, disposition `RECORD_CONFIRMED_SENT` with independently obtained provider receipt or `LEAVE_UNCERTAIN_NO_RESEND`. Office cannot assert provider failure without evidence. A manual request to try again uses the existing explicit manual send review and a new logical ordinal only after the actor sees the uncertain earlier message, enters a reason, and the current policy allows a deliberate duplicate-risk send; the UI says **The earlier message may have been sent. Sending again could contact the recipient twice.** Never auto-resend uncertain native pushes. This review does not block the scope's pause/resume or unrelated eligible rows; it only retains ownership of that exact logical item. Native in-app access remains the fallback. Accepted history/budgets remain once, no unknown-as-zero shortcut.

At resume/expiry re-evaluate exact report set/revision, worker worked evidence, current need/replies, source authorisation/finalisation, recipient, actor, current device/membership/preferences, logical accepted sends, age, cutoff, request expiry and global push timing. Retire obsolete initial/reminder targets. Choose at most one currently due step for a logical question; no initial+reminder catch-up burst and no reset.
